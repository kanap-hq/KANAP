# Server clusters (IT Ops Part B)

- **Mark clusters**: set `is_cluster = true` on a server (Servers workspace toggle or POST/PATCH `/servers`).
- **Membership**: use `GET /servers/:id/members` to view and `POST /servers/:id/members` with `server_ids: string[]` to replace members (only non-cluster hosts; `remove_operating_system: true` removes the cluster's operating system with the first members). A cluster with members cannot be switched back to a plain server, a member cannot become a cluster, and a cluster with members has no operating system (a cluster with no declared member may keep one). `GET /servers/:id/clusters` lists clusters that include a host.
- **Assignments (model)**: an application deployment can be assigned to a cluster. It is one row in `app_asset_assignments`, on the cluster, and the cluster is itself a server of the application. Members inherit at read time, nothing is copied: a member's effective rows are its own plus those of its clusters, marked `inherited` with `via_clusters`. A member added later inherits at once; a member taken out loses what it inherited; a retired member inherits nothing and a retired cluster passes nothing on. One effective row per (deployment, server, role); a direct row wins over an inherited one. The single definition is `effectiveAssignmentsSql` in `backend/src/app-asset-assignments/effective-assignments.ts` (a SQL fragment, `tenant_id` on every join, batched by `= ANY`), with `groupableAssignmentsSql` for the direct rows that could move to their cluster (a deployment and role on every member in service of a cluster in service that has at least two).
- **Readers**: every source file that reads the table is listed in `backend/src/app-asset-assignments/assignment-readers.inventory.ts`, as `effective` (reads through `effectiveAssignmentsSql`) or `direct` (the stored rows on purpose, with a reason). `__tests__/assignment-readers.inventory.spec.ts` fails on an unlisted reader and on a stale entry. The effective readers: Deployments and Operations tabs, connection map preselection and tiers, interface map servers, asset list count, hosting types, vulnerabilities, end of support, technology reach and application conversion (clusters excluded, a cluster gives its members), administration view, locations, contracts, Knowledge and the assistant. A new reader goes through the effective rows unless it has a reason not to.
- **Assignments (writes)**: `backend/src/app-asset-assignments/cluster-assignment-rules.ts` holds the rules shared by the service and the assistant, inside the write's transaction. A member gets no direct row for a deployment and role one of its clusters carries (`409 assignment_inherited`, `params.cluster`). A row written to a cluster in service replaces the direct rows of the same deployment and role on its members in service (absorption, each deletion audited), keeping the earliest `since_date` and adding their distinct notes; the answer lists them in `absorbed`. A writer first locks the clusters it decides on (`lockAssignmentClusters`, `FOR NO KEY UPDATE` by id), as the cluster switch and the members endpoint do. The screen asks the member question (`useClusterAssignmentQuestion`) before the write; the API and the assistant apply the rules without asking. Deleting a member that only inherits rows is allowed. Endpoints: see `doc/api-reference.md`, "App Server Assignments".
- **Connections (model)**: an endpoint, a server of a multi-server connection or the equipment of a hop written on a cluster is one stored row, on the cluster (`connections.source_asset_id` / `destination_asset_id`, `connection_servers`, `connection_legs.equipment_asset_id`). Members inherit at read time, as for assignments: `effectiveConnectionAssetsSql` in `backend/src/connections/effective-connection-assets.ts` returns one row per (connection, asset, part, hop order), `part` being `source`, `destination`, `server` or `hop`, with `inherited` and `via_clusters`. A retired member inherits nothing, a retired cluster passes nothing on, a direct row wins over an inherited one. A cluster sees nothing of its members.
- **Connection readers**: `backend/src/connections/connection-asset-readers.inventory.ts` lists every source file that reads the stored server or hop tables, the hop equipment column or the effective definition, as `effective` or `direct` (with a reason). `__tests__/connection-asset-readers.inventory.spec.ts` fails on an unlisted reader and on a stale entry. Effective readers: the Network tab of an asset (`GET /connections/by-server/:id`) and the servers of a connection linked to an interface binding. The connection map reads the stored rows and draws the members itself.
- **Connections (writes)**: `backend/src/connections/connection-cluster-rules.ts`. A server-to-server connection whose source and destination are the same asset is refused (`400 connection_same_endpoint`); an existing loop can still be renamed, but changing a side may not keep it looped. A multi-server list drops the members in service of a cluster in service it also holds (`absorbClusterMembers`, input order kept, a member of two listed clusters absorbed once under the first cluster by name); the answer of `POST` / `PATCH /connections` lists them in `absorbed`. A list left with fewer than two assets is refused (`400 connection_min_servers`). No lock: a membership that changes afterwards only leaves a row too many, which the read deduplicates. The screen asks the member question (`useClusterConnectionQuestion`: connect the cluster or this server only) before the write, for an endpoint, a listed server and the equipment of a hop; it does not ask when the other side already holds the cluster or another of its members.
- **Connection map**: `GET /connections/map` adds the members in service of every drawn cluster, even when no connection names them (`implicit_member: true`), and gives each cluster `member_server_ids` (its members in service). The page draws them under the cluster with dashed lines, folds the implicit members beyond ten per cluster into a `+N` on the cluster label (`connectionMapMembers.ts`; a member picked as a start or named by a connection is never folded), and turns a member picked as a start into a start for its clusters too.
- **Placement (VMs)**: `backend/src/assets/placement-rules.ts`, shared by every writer of an `asset_relations` `contains` (relation replacement, single link, the assistant, Netbox), inside the write's transaction. R1: a `contains` written by a cluster in service replaces the `contains` of its members in service towards the same assets, each removal audited, reported in `replaced_host_links`. R2: a `contains` from a host in service towards an asset one of its clusters in service already contains is refused (`409 placement_inherited`, `params.cluster`); a link already stored is written again without refusal. R3: other double containers are reported (`double_containers` on the write, `also_contained_by` on each contained row of `GET /assets/:id/relations-tab`), never refused; a retired container does not count. Lock order: clusters (`lockAssignmentClusters`), then the source asset, then the hosts whose links are removed. The screen asks the placement question (`usePlacementQuestion`: place in the cluster or this host only) before a `contains` or `contained_by` from a member host. Netbox: attaching a VM to its matched cluster replaces the link of a member host that carries it (R1); the preview shows it as a `placement` diff (before: the hosts, after: the cluster).
- **UI**: the asset list shows a member's cluster names and an icon for a cluster; its **Add asset** button is a menu with **Add cluster** (creation opens with the switch on, `?cluster=1`). The Operations tab of a cluster starts with the Members table and its dialog (plain assets only, the cluster itself excluded); a member's Operations tab starts with its Cluster membership, shown only when it belongs to a cluster. Adding the first members to a cluster that carries an operating system asks before sending `remove_operating_system: true`. Deleting an asset first reads `POST /assets/delete-check` and lists the memberships, members and relations it removes. The Connection Map's "View cluster" opens the Operations tab. The connection pickers mark clusters (`ClusterMark`) and list their members (`include=member_names`). The Network tab marks a connection a member inherits with "via" and its clusters, names the hops the asset is the equipment of, and lists the servers of a multi-server connection. The Dependencies tab flags a contained asset that has another container in service.
- **List, filter and CSV**: membership is read from `asset_cluster_members` only (real clusters). The `cluster` filter takes names, `__cluster__` and `null`. The asset CSV column `cluster` ("Cluster Membership") holds comma-separated cluster names (case ignored): the export writes the real clusters, the import resolves each name to exactly one cluster (`CSV_CLUSTER_NOT_FOUND`, `CSV_CLUSTER_AMBIGUOUS`, `CSV_CLUSTER_NOT_A_CLUSTER`, plus `cluster_member_self`, `cluster_member_is_cluster`, `cluster_os_with_members` as row errors) and writes through `replaceClusterMembers`: enrich adds, replace also leaves the clusters the cell does not name, an empty cell changes nothing. The technology-links CSV refuses the operating-system mark only on a cluster with members.
- **Rules in one place**: `backend/src/assets/asset-rules.ts` serves PATCH, the members endpoint, both CSV imports, `setOperatingSystem` and the assistant's `cluster_members` relation.
- **Migrations**: `1854900000000-cluster-membership-repair` removes memberships the rules forbid (cluster no longer a cluster, member that is a cluster, self). `1855000000000-cluster-membership-from-legacy-text` turns the legacy `assets.cluster` text into memberships when a name is exactly one cluster (not the asset itself, not a cluster with an operating system) and empties the text once every name is taken; the column stays until a later release drops it.
- **Impact**: a cluster that falls takes its members in service (`member` edge); a fallen member makes its cluster degraded; a cluster down (no member standing) takes its applications and what it contains. See `doc/api-reference.md`, "Impact".
- **Counts**: a cluster counts its own vulnerabilities plus its members' direct links in service (`assetCountLinksSql`, `member_totals`). A technology's servers are the assets in service that carry it, installed or carried, clusters excluded, the same number in the list, the record's Servers badge, the end of support report and the assistant; a piece of hardware is not one of its own servers. The Servers tab lists a cluster (not counted) with one carried line per version and `via_assets`. Version `servers` and the Vulnerabilities page's Servers column stay the direct links.
