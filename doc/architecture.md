## Summary
KANAP is a NestJS API, a Vite/React single-page app and an Astro marketing site in front of one PostgreSQL 15 database. The same code base ships in two deployment modes selected at runtime: `multi-tenant` (the cloud SaaS, one shared database with row-level security per tenant) and `single-tenant` (on-premise, one tenant, no platform layer). See [Deployment Modes](#deployment-modes).

Production topology layers Cloudflare in front of a host Nginx front door for routing/TLS. Platform-administration traffic uses a dedicated host (`platform-admin.kanap.net`) served by the same NestJS/Vite stack but bound to a system tenant instead of a customer tenant.

## Deployment Modes
- `DEPLOYMENT_MODE=single-tenant` selects on-premise mode. `multi-tenant`, or leaving the variable unset, selects cloud mode. Any other value stops the API at start and the message names the accepted values. Flags are computed once in `backend/src/config/features.ts` (`parseDeploymentMode` in `backend/src/common/deployment-mode.ts`) and are the single source of truth:
  - `SINGLE_TENANT`, `DEPLOYMENT_MODE`
  - `STRIPE_BILLING` (multi-tenant only, needs `STRIPE_SECRET_KEY`)
  - `ENTRA_SSO` (`ENTRA_CLIENT_ID` present)
  - `EMAIL_ENABLED` (a transport is configured, see Notifications)
  - `AI_CHAT_ENABLED`, `AI_MCP_ENABLED`, `AI_SETTINGS_ENABLED` (booleans), `AI_WEB_SEARCH_READY` (`BRAVE_SEARCH_API_KEY` present)
  - `TECHNOLOGY_CATALOG_SYNC_ENABLED` (the living catalog of technologies reads endoflife.date; env value when set, otherwise true in the cloud and false on-premise; `ENDOFLIFE_API_BASE_URL` optional)
  - `VULNERABILITY_FEED_ENABLED` (the NVD feed and the exploitation signals, one switch; env value when set, otherwise true in the cloud and false on-premise; `NVD_API_KEY` and `NVD_API_BASE_URL` optional; `KEV_FEED_URL`, `EPSS_FEED_URL` and `EUVD_BASE_URL` optional, an empty value keeps the default address)
  - `IMPORT_XLSX` (the data imports read an Excel workbook, its first sheet, as well as a CSV file; env value when set, otherwise true; false brings back the CSV-only imports)
- Backend gates live in `backend/src/common/feature-gates.ts` (`throwFeatureDisabled()`, `MultiTenantOnlyGuard`, `throwNotAvailableInMode()`). The SPA reads the same flags through `GET /api/config/public` and the `useFeatures()` hook (`frontend/src/config/FeaturesContext.tsx`) to hide routes and navigation.
- Single-tenant consequences: Host-header tenant resolution is skipped and `DEFAULT_TENANT_SLUG` (default `default`) is used; the tenant, its administrator and a local subscription are auto-provisioned on first boot (`backend/src/main.ts`), the tenant with the default global chart of accounts as at cloud activation (`tenants/single-tenant-provisioning.ts`, only when it creates the tenant); trial signup endpoints, the platform console and Stripe are off; SMTP email is accepted.
- Compose files: `infra/docker-compose.yml` (dev, with `db`), `infra/compose.qa.yml` / `infra/compose.prod.yml` (cloud), `infra/compose.onprem.yml` (api + web only, loopback ports 8080/8081).
- The full feature gate inventory and the on-premise design live in `doc/on-premise/technical-design.md`; operations in `doc/on-premise/README.md` and `doc/on-premise/operations-internals.md`. CI (`.github/workflows/ci.yml`) builds both modes.

Details in `doc/frontend-architecture.md`.
- **Backend API (`api`)**: NestJS + TypeORM on Node 24. Modules by domain:
  - Budget: spend (OPEX), capex, contracts, accounts / chart of accounts, currency, freeze, analytics, billing, dashboard
  - Master data: companies, departments, suppliers, contacts, locations, users, business processes, master-data operations
  - Portfolio: requests, projects, teams, contributors, time entries; tasks
  - IT Landscape: applications, app instances, assets, connections, interfaces and bindings, IT Ops settings, incidents
  - Knowledge: documents, libraries, folders, types, workflows, integrated documents
  - AI: chat, MCP server, control plane (agents, capabilities, approvals), GLPI and PRTG providers, model registry
  - Platform and admin: tenants, roles, permissions, auth (local + Entra), audit, branding, CoA templates, ops, scheduled tasks, cleanup
  - Cross-cutting: tenancy, storage, email, notifications, i18n, public endpoints, health, seed
- **Data store (`db`)**: PostgreSQL 15. Containerized in dev only; host-installed on QA/prod. Row-level security on every tenant-scoped table.
- **Marketing (`marketing`)**: Astro 7 static site in `marketing/web`, built with Node 24 and served by Nginx. Content notes live next to the site (`marketing/web/*.md`).
- **Integrations**: CSV import/export; GLPI (ticketing) and PRTG (monitoring) providers for agents; Microsoft Entra (SSO + directory sync); Stripe (billing, cloud only); Resend or SMTP (email); Brave Search (web search); S3-compatible object storage; MCP (inbound server and outbound bridge).

## Ingress & Routing (prod intent)
- Cloudflare:
  - DNS and TLS termination for `kanap.net`, `qa.kanap.net`, `dev.kanap.net`, and their subdomains.
  - Proxies HTTPS traffic to the origin Nginx instance (QA/prod servers) or to the Cloudflare Tunnel endpoint (local dev).
- Origin Nginx vhosts (`infra/nginx/host/prod.conf`, `qa.conf`, `cloudflare-real-ip.conf`):
  - `kanap.net` and `www.kanap.net` -> `marketing` (127.0.0.1:8082)
  - `location /api/` on every vhost -> `api` (127.0.0.1:8080) with the `/api/` prefix stripped (avoids CORS for signup)
  - `*.kanap.net` -> `web` (127.0.0.1:8081), one subdomain per tenant. `platform-admin.kanap.net` is served by this wildcard block; the backend distinguishes it by `PLATFORM_ADMIN_HOST`.

## Environments
- Dev (local):
  - Fully containerized: `db`, `api`, `web`, and `marketing` via `infra/docker-compose.yml`. The `dev-proxy` compose profile adds an Nginx that mirrors QA/prod routing (`infra/nginx/dev/nginx.conf`).
  - Cloudflare Tunnel terminates HTTPS for `dev.kanap.net` and `*.dev.kanap.net` and forwards to that proxy on `localhost:80`. The tunnel is host-side, not committed.
  - `lvh.me` and `*.lvh.me` remain available as an HTTP-only fallback without Cloudflare.
- QA (`qa.kanap.net`) and Prod (`kanap.net`):
  - DNS and TLS managed by Cloudflare (proxied records for the root and wildcard).
  - Host-installed Nginx (ports 80/443) and host-installed Postgres; the API reaches Postgres through `host.docker.internal`.
  - Containers for `api`, `web`, and `marketing` only, bound to loopback; host Nginx proxies to them.
  - Deploy = `git pull`, `docker compose --env-file backend/.env.<env> -f infra/compose.<env>.yml build api web marketing`, then `up -d api web marketing`. The public site is the `marketing` service: a deploy that leaves it out keeps serving the previous site.
- On-premise: `infra/compose.onprem.yml` with `DEPLOYMENT_MODE=single-tenant`; the customer provides Postgres, reverse proxy and S3-compatible storage.
- Migrations: in dev the compose command runs `typeorm migration:run` before `start:dev`. QA, prod and on-prem images start with `scripts/migrate-and-start.js` (waits for the database, runs migrations, honours `SKIP_MIGRATIONS`), then start the API. Only the connection is retried, while the database is not ready or goes away during the migrations (ECONNRESET, ECONNREFUSED, PostgreSQL 57P01, 57P03 and class 08; `MIGRATION_MAX_ATTEMPTS` tries in all, 30 by default, `MIGRATION_RETRY_DELAY_MS` apart, 2 s): a migration that fails on its own stops the entrypoint at once (exit 1) and logs its message and the start of the failed statement. The pending migrations run in one transaction, so the database is left as it was before that start; the container's restart policy runs the entrypoint again. Then the API starts: in the same process, or as a cluster of `API_WORKERS` processes forked once the migrations ran (see [Several API Processes](#several-api-processes)). TypeORM also has `migrationsRun: true` in a single process (a no-op after the entrypoint) and `false` in a cluster worker: TypeORM takes no lock, two processes migrating at once would collide.
- Images: the API image (`backend/Dockerfile`) has four stages. `base` holds the Alpine system, the document converters (pandoc, typst, inkscape) and the fonts; `build` holds every dependency and the compiled `dist/`; `production-dependencies` prunes the development dependencies; `runtime` is the default target and the content of the published `kanap-api` image: compiled code, production dependencies, the start-up script and the demo data set, without sources or development tools, started as the `node` user. `dev` is the full tree: the local stack runs it, and the published `kanap-api-tools` image holds it for maintenance commands that run TypeScript (the `tools` service of `infra/compose.onprem.yml`). The on-premise, QA and prod compose files pull the images of one version from `ghcr.io/kanap-hq`, built by CI from the version tag (`doc/releasing.md`); `infra/compose.onprem.build.yml` builds them on the server instead (`*:local`). Every base image in the Dockerfiles and compose files is pinned to the digest of its multi-architecture index (`name:tag@sha256:...`); Dependabot proposes the new digests and `.github/scripts/check-image-pins.sh` checks the pins in CI. CI builds the API (runtime and dev), web and marketing images on every change that touches them. The server compose files add a health check on `api` and `web` (status only, nothing restarts on it), Docker logs capped at 5 files of 10 MB (`json-file`), `no-new-privileges`, a process limit and `cap_drop: ALL` (the web container keeps the few capabilities nginx needs to start and switch user). The web container sends the security headers of `frontend/nginx/security-headers.conf` and hides the nginx version (`server_tokens off`). Each release can attach a component inventory and third-party notices (see `doc/sbom.md`).
- Stop: the image starts the entrypoint with the exec form of `CMD` and the compose files add `init: true`, so `docker stop` reaches Node; `stop_grace_period: 30s` leaves the drain time (`SHUTDOWN_DRAIN_TIMEOUT_MS`, default 20 s). The cron jobs stop at once and the API stops accepting connections; the requests in flight finish; 1.5 s after the last response (the work it started without awaiting gets going), the work left is given until 2 s before the end of the drain time: notification chains and queued FX refreshes (tracked, `common/background-work.ts`), running scheduled tasks (a run still going then is recorded as failed, "interrupted", instead of staying "running" for an hour), the notifications those tasks started, then the email queue (emails still queued at the deadline are lost, logged). Then the app closes and the process exits 0; past the drain time it exits 1. The image used to start Node through `sh -lc`, which never passed SIGTERM on: every stop waited 10 s and was killed, which cut requests, queued emails and running tasks alike; the locale that login shell exported is now set in the image (`LANG=C.UTF-8`, `CHARSET`, `LC_COLLATE`).

## Non-Functional Concerns
- Security: local password auth + JWT, optional Microsoft Entra SSO per tenant, audit logging for all writes, RLS on every tenant table.
- **Security events** (`backend/src/audit/security-events.ts`): the tenant's `audit_log` also holds sign-in and session events and exports, without a schema change. Sign-in events use `table_name = 'auth'` and one of `login`, `login_failed`, `logout`, `refresh_denied`, `password_reset_requested`, `password_reset_completed`, `sso_login`, `sso_login_failed`; the account in `record_id` and `user_id` when the request named a known one; a short code from a fixed list in `source_ref` (`bad_password`, `unknown_user`, `disabled`, `invalid_token`, `too_many_attempts`, ...); `after_json = { ip, user_agent }`, the address from `clientAddress()` (`common/client-address.ts`) when it is a valid IPv4 or IPv6 address of at most 45 characters (null otherwise) and the agent cut to 200 characters. No password, token, hash, link or e-mail address is stored (an attempt on an unknown address keeps its reason only). `SecurityEventsService` writes them after the outcome, in a transaction of its own (a refused sign-in rolls its transactions back), without the response waiting, and never rejects (`common/never-rejects.ts`). Paths covered: password sign-in (the platform console signs in the same way, on its own tenant), the provisioning token exchange, sign-in with Microsoft (callback and session; a failure is recorded only in the tenant a verified state or hand-off names, or in the host's tenant when Entra sign-in is set up for it: a request where nothing verifies writes nothing, and both routes carry their own sign-in rate limit, `RATE_LIMITS.ssoSignIn`, 60 a minute per client address, as wide as the password sign-in's because the staff of one organisation often share one outbound address), session renewal, sign-out, password reset (invitations end there too). A request without a tenant writes nothing. Exports: every route whose path ends with `/export` (`POST /export` included), and every other route that sends a file the server produces, marked `@ExportRoute()` (`GET /incidents/:id/report`), writes `table_name = 'export'`, `action = 'export'`, `after_json = { resource, path, query, ip, user_agent }` (address and agent as for sign-in events) through `ExportEventsInterceptor` (`common/request-pipeline.ts`), in the request transaction before the handler: a failed or refused export leaves no row. `query` is the query as sent (keys sorted, `ctx` as its id, never the body), at most 2,000 characters (the longest entries dropped first, `truncated: true`). One UPDATE then adds what was sent: `format`, from the response's `Content-Type` (`csv`, `xlsx`, `pdf`, `docx`, `odt`, `markdown`, else the bare media type, at most 40 characters), and `rows: n` when the handler reports its count. A handler that answers itself (`@Res()`) calls `await completeExport(res, { rows: n })` (`audit/export-events.interceptor.ts`) after setting its headers and before sending (the budget file): the request finalizer (`common/request-finalizer.middleware.ts`) rolls back, on the response's `finish`, a transaction whose commit has not started, so no database work may follow the response. A `@Res()` handler that does not call it keeps a row without `format`. For a handler that returns a value, the interceptor runs the update after the handler, before TenantInterceptor commits (the `Content-Type` is then the one `@Header` set, absent without it); after a response that has already left it adds no step. The update runs in the request's query runner read again at that moment (skipped when it was released), inside a savepoint: a failed update leaves the row as written and logs a warning. Role changes (create, rename, permissions, duplicate, delete) are logged on `roles` with before, after and actor. The `auth-event-retention` task deletes `auth` rows older than 365 days; the rest of `audit_log` is kept. A password sign-in on an unknown address or on an account without a local password runs the same argon2 check as a wrong password, against a fixed hash (`FIXED_PASSWORD_HASH`, `auth/auth.service.ts`), so the response time does not depend on the account existing. A password reset request for a known account issues its link and sends its e-mail after the response (`AuthController.deliverPasswordReset`, `@NeverRejects()`, its own connections in the request's tenant, no entity manager of the request) and then records its event: a link that cannot be saved or an e-mail that cannot be sent is an error line in the server log (transport and error code; the link, the token and every e-mail address are left out) and the reason `email_not_sent` (also given when the address is on a reserved `.example` domain, where nothing is sent), so the answer is the same for every address whether the e-mail goes out or not.
- **CORS**: one origin policy (`backend/src/common/cors-policy.ts`, parsing in `backend/src/common/env.ts`) shared by the CORS middleware and the cookie-based session routes (`POST /auth/refresh`, `POST /auth/logout`). Accepted: exact `CORS_ORIGINS` entries, the application address (`APP_BASE_URL`, or the tenant's address), the address of the request itself, and in multi-tenant mode wildcard patterns (`https://*.kanap.net`) for the targeted tenant only (single-tenant: patterns still accepted with a start-up warning). A refused origin gets a 403 without CORS headers. Run mode (`APP_ENV`): production fails to start without `CORS_ORIGINS` and `APP_BASE_URL`; development allows every origin when `CORS_ORIGINS` is empty; any other value applies the production origin rules and warns at start (with neither `CORS_ORIGINS` nor an application address, every origin stays allowed in this version).
- **Rate limiting**: `ThrottlerModule` (60 s window, 10 requests) is always registered; a custom guard (`backend/src/common/rate-limit.guard.ts`) applies it per controller (auth, public signup, applications, document export) and short-circuits when `RATE_LIMIT_ENABLED=false`. `RATE_LIMIT_TRUST_PROXY` gives the number of reverse proxies in front of the API (`false`, `true` for one, or 1 to 3) and sets Express `trust proxy` to it, so `req.ip` is the entry the outermost trusted proxy appended to `X-Forwarded-For` (`common/client-address.ts`). Unset or invalid, the default is one proxy in single-tenant mode and none in multi-tenant mode (QA and prod set it explicitly); the start-up log has one `[RATE-LIMIT]` line that says which applies. With one API process the counts live in its memory; with several they live in the database (see [Several API Processes](#several-api-processes)).
- **Database connection management**: per API process, pool `DB_POOL_MAX` (20, at least 2), `DB_POOL_MIN` (2), `DB_POOL_IDLE_TIMEOUT` (30 s), `DB_POOL_CONNECTION_TIMEOUT` (10 s), configured in `backend/src/app.module.ts`. With `API_WORKERS` processes the API can open `API_WORKERS × DB_POOL_MAX` connections; see [Database Pool](#database-pool).
- **Resilience**: request-level transactions with guaranteed connection release; fail-fast connection timeouts prevent hung requests.

### Several API Processes
One Node process runs all the JavaScript of the API on one thread: while a request computes, every other request of every tenant waits (measured on 2026-10-01: a trivial request waited up to 2 s behind a list rebuild, plan planning/perf-scale lot 4A). `API_WORKERS` runs several API processes in the same container.

**Run mode: Node cluster in one container.** `API_WORKERS` (default 1, at most 16) is read by the entrypoint `scripts/migrate-and-start.js`. With 1 nothing changes: the API runs in the entrypoint's process. With N > 1 the entrypoint runs the migrations, then becomes a cluster primary (`backend/src/common/cluster/cluster-primary.ts`) and forks N workers, each a full API process (`dist/main.js`) with its own pool. Once the workers start, the primary serves no request and holds no database connection. It hands each worker `KANAP_WORKER_ID` (1 to N), `KANAP_WORKER_COUNT` and `KANAP_CLUSTER_STARTED_AT`, forks a dead worker again in its slot after 1 s, and exits 1 after 5 worker exits within 60 s so the container restart policy takes over. On SIGTERM it forwards the signal, waits for the workers to drain (drain time + 5 s), kills a worker still running, then exits. Connections are spread by the cluster module, round robin on Linux; a request stays on the worker that got its connection, so behind a proxy that opens one connection per request (the host nginx examples of this repository) requests spread evenly.

Why not several containers behind nginx: an on-premise customer runs one compose file and one reverse proxy of their own. Several containers would mean an upstream block with one port per container in the customer's proxy, a migration lock between containers, and N copies of everything that runs once. The cluster keeps one container, one port, one log stream, one memory limit, and one place where the migrations run. The coordination below lives in the database anyway, so a second container (an operator running two by mistake, or a future scale-out) stays safe for jobs, notifications, provisioning and migrations; only the per-process items accepted below would count per container.

**Lead process.** The single process, or worker 1 (`isLeadProcess()` in `process-role.ts`), does the once-per-start work: the startup scheduled tasks (`runOnStartup`, today `lifecycle-status-sync`) and the connection budget check. It alone prints the start-up report lines (`[ENV]`, `[SECRETS]`, `[RATE-LIMIT]`, `[CORS]`, `[DB]`, `[SECURITY]`, an administrator account left unchanged); a line that reports a change (a tenant, an account or a subscription created) is printed by the process that made it. Nest's own lines (routes, cron jobs scheduled, application started) describe each process and are printed by each.

**Inventory: what assumed one process, and the decision for each.**

| Item | Where | One-process assumption | Decision |
|---|---|---|---|
| Migrations at start | `scripts/migrate-and-start.js`, TypeORM `migrationsRun` | TypeORM takes no lock; every process would migrate | Run once by the entrypoint before any worker starts; `migrationsRun` is `false` in a cluster worker |
| Integrated-document rollout at start | `migrate-and-start.js` | | Already under a session advisory lock; runs once, in the entrypoint |
| Start-up writes: admin seed, single-tenant tenant, administrator and subscription | `main.ts` | Check then insert: two processes could both insert | Under one session advisory lock (`common/cluster/startup-lock.ts`): processes take turns, the later ones find the rows. The `SEED_ADMIN` path no longer returns from `bootstrap()` when the tenant is missing (the API never listened) |
| Scheduled tasks (14: expiration warnings, weekly reviews, Entra sync, agent ingestions and sweeper, retention, previews, search reindex, attachment and ghost cleanup, lifecycle status sync, list-context purge, Netbox sync) | `ScheduledTasksService` | Every process schedules every task. The session advisory lock of `executeTask` only skips a run that overlaps another: a fast task could end before the next process tries it and run once per process | Each cron tick is claimed once in `scheduled_tasks.last_tick_at` (the tick's scheduled time, the same in every process): one process moves it and runs, the others skip. The overlap lock stays for long runs and manual triggers. A stored tick more than a day ahead (a clock that was ahead, a VM restored from a snapshot) is claimed over, with a warning; a lost claim is logged only with `LOG_LEVEL=debug` |
| Task registration at start | `ScheduledTasksService.onApplicationBootstrap` | Insert of a missing task by two processes: unique violation, the second process failed to start | `INSERT ... ON CONFLICT (name) DO NOTHING`: the second insert adds nothing, and no failed statement reaches the log |
| Cron change or disable from the admin console | `updateTask` | Reaches the process that answered only | The claim also checks the stored cron and `enabled`: another process reschedules or drops its job at its next tick instead of running |
| Startup tasks (`runOnStartup`) | `main.ts` | Once per process | Lead process only |
| Ops metrics | `OpsMetricsStore`, `DbMetricsService` | Per process: the snapshot showed the process that answered | Each process publishes a summary every 15 s to `ops_process_metrics` when N > 1; the snapshot lists and adds them up (see Supervision) |
| Liveness route `/health` | tenancy middleware, `TenantInitGuard` | | Never looked up and `@Public()`: no tenant lookup and no tenant transaction, so polling it costs no connection and a saturated pool does not make the API look dead (it used to take two connections per call in single-tenant mode, and answer 503 under saturation) |
| Event notification dedupe (5 minutes per recipient, item and trigger) | `NotificationsService` | In-memory map: two quick changes answered by two processes both mailed | Claimed in the database, `notification_dedupe` (tenant-scoped, RLS forced), one upsert per claim, committed before the email goes out. If the claim fails the process falls back to its in-memory window. Expiration warnings were already deduplicated in the database (`audit_log` rows under an advisory lock); the weekly review runs once per tick and stamps `weekly_review_last_sent_at`; share notifications have no dedupe, as before |
| HTTP rate limits (login 60/min, sign-in with Microsoft 60/min, refresh 120/min per address and tenant, password reset, provisioning exchange, public forms, exports and imports, saved list filters) | `RateLimitGuard`, `ThrottlerModule` | In-memory counts: N processes, N times the budget | One `ThrottlerModule`, in `app.module.ts`: no other module imports its own (it would give its routes a separate in-memory counter, as `AuthModule` once did for the sign-in routes; `auth-rate-limit-processes.integration.spec.ts`). One process: in memory, unchanged. Several: `rate_limit_hits` (UNLOGGED, keys are SHA-256 hashes), one upsert per hit on a second pool connection, outside the request's transaction (a refused login rolls the request back, a count written inside it would be lost): a rate-limited request holds two connections for a moment, hence `DB_POOL_MAX` ≥ 2. Fixed window: at a window boundary up to twice the limit can pass within seconds (the in-memory counter expires each hit on its own). When the database does not answer within 1.5 s (pool exhausted, database down) the hit is counted in the process's memory, with one warning a minute: the limit then holds per process |
| Password sign-in attempts per account and client address (5 refused in 15 min, then 15 min refused; fixed windows, as for the other HTTP limits) | `LoginAttemptLimit` (`auth/login-attempt-limit.ts`) | In memory | One process: in memory (`MemoryHitCounter`). Several: `rate_limit_hits` with the same upsert (`DatabaseHitCounter`), keys are SHA-256 hashes of tenant, client address and the identifier typed. The attempt counts when it starts, before the password check, so attempts at the same moment cannot pass the limit together; an attempt that ends in an error other than a refusal (server error, database unavailable) is taken back afterwards in one statement (`release`, same window, key not blocked), the earlier refusals stay counted. The fifth refusal blocks the pair for 15 minutes (`block`) and writes one `login_failed` event with the reason `too_many_attempts`; the attempts refused during the block write nothing. A success clears the pair (`clear`). Same 1.5 s fallback to the process's memory; a block goes to memory only when the database does not take it |
| Session renewals per refresh token (30 a minute, then refused for the next 60 seconds; fixed window) | `RefreshSessionRateLimitGuard` (`auth/refresh-session-limit.ts`) | In memory: with several processes, each process counts on its own | One process: in memory (`MemoryHitCounter`). Several: `rate_limit_hits` with the same upsert (`DatabaseHitCounter`), keys are SHA-256 hashes of tenant and refresh token: the token is never stored in clear. Runs after the origin check and before the address limit of `POST /auth/refresh` (per address and tenant, `TenantRateLimitGuard`): a renewal it refuses does not count against the address, so a client that loops does not take the budget of its neighbours. A request without a token is not counted here. Same 1.5 s fallback to the process's memory |
| Built-in AI rate limits (per tenant per minute, per user per hour) | `AiBuiltinRateLimiter` | In memory | Accepted per process: the built-in model is a cloud feature (cloud runs one process), and the monthly quota that bounds the cost is reserved in the database (`ai_builtin_usage`) for every message. With N processes the per-minute and per-hour bursts are N times higher |
| MCP API key rate limit | `AiMcpRateLimiter` | In memory | Accepted per process: it protects each process from a runaway client; the total is N times the configured limit |
| Email queue and pacing (700 ms between messages for Resend) | `EmailService` | One queue | Accepted per process: N processes send up to N times faster; Resend `429` answers are retried with backoff. ### Database Pool
- **Pool per process.** `DB_POOL_MAX` (default 20, at least 2: a scheduled task holds one connection for its lock while its queries take another, and with several processes a rate-limited request takes a second one for its count; a lower value is raised to 2 with a warning at start) connections per API process. At start the lead process checks `API_WORKERS × DB_POOL_MAX ≤ max_connections − reserved (superuser_reserved_connections + reserved_connections) − 10` and logs one line, a warning when it does not fit, with a pool size that would (never under 2; when even 2 does not fit, fewer processes or more `max_connections`) (`common/db-pool-budget.ts`); the API starts anyway. Since the SQL list engine (step 2) requests hold their connection for milliseconds: at 50 users on 5,000 budget lines, two workers used 15 connections in all and four workers 17, so with 4 workers a pool of 10 each is enough; keep the total under about 80.
- **PgBouncer** (transaction pooling) becomes worth it past about 80 connections from the API, or when other applications share the server. The request path is compatible: the tenant and the bounded waits are set with `set_config(..., true)` inside each request's transaction and end with it. Not compatible as is, to change first: the session advisory locks held across statements outside a transaction (`ScheduledTasksService.executeTask`, the Netbox running lock, the startup provisioning lock, the integrated-document rollout), `withTenantExecution({ transaction: false })` which sets the tenant for the session (the Netbox sync; under transaction pooling the next statement can land on another server connection, and the setting stays on one another client then gets), and the migrations (run them on a direct connection). Prepared statements are unnamed (node-postgres default), fine with PgBouncer.

### Supervision
The ops snapshot (`backend/src/admin/ops/`, plan planning/perf-scale lot 4D) is served to platform admins (`GET /admin/ops/snapshot`, cloud) and, with `OPS_METRICS_TOKEN` set (24 characters or more; a shorter one leaves the route disabled and the start says so), to a monitoring tool in both modes: `GET /api/ops/metrics` with `Authorization: Bearer <token>` (404 without the setting). That route is never looked up by the tenancy middleware and opens no tenant transaction, and leaves out the messages of the recent server errors (they can quote internals; the platform console keeps them). The snapshot holds, per process:
- requests per window (1, 5, 15 minutes), status classes, p50 / p95 / p99 per route pattern over 5 minutes (30 busiest routes);
- event loop lag over the last full minute (`eventLoopLagMs`: what a 10 ms timer is late by, p50 / p95 / p99 / max; it used to count the timer resolution and was never reset) and the worst minute of the last five (`eventLoopLag5m`);
- the pool (`db.pool`): connections in use now and highest over a minute, requests waiting, the time to get a connection (p50 / p95 / max over a minute, p95 over 5 minutes, timed around the pg pool's `connect`; each percentile is capped at the maximum measured over the same window), connections the pool could not give over 5 minutes;
- PostgreSQL activity of the API's connections (`pg_stat_activity` by application name) and database counters, read every 10 s at most;
- `health`: `ok`, `warn` or `critical` with the alerts below.

The snapshot answers when the pool is saturated, when it matters most: the figures above held in memory are always served; the pg_stat reads and the other processes' rows are not read while the process's pool is saturated (every connection open and requests waiting: they would queue behind them), and otherwise given 1 s each, in parallel. Without them the last values read are served, flagged `db.statsStale` (with `db.statsError`), and the other processes are left out.

With several processes each one publishes a summary every 15 s (UNLOGGED table `ops_process_metrics`; its row is deleted when the process stops, a killed process ages out after 45 s, rows older than 10 minutes are purged by the publishers and rows older than a day at every start). The snapshot adds `processes` (each live process, the newest row per worker slot: a worker forked again after a crash leaves an older row behind) and `aggregate`: sums for requests, memory and the current pool use, the fullest pool over the minute with its process (`inUsePctMax1m`, `fullestProcess`; the sum of the per-process highs is given as `inUseMax1mUpperBound`, an upper bound since the highs need not coincide), the worst process for the event loop, merged latency histograms for the p95s (a percentile read from the histogram is the upper bound of its bucket; the pool wait p95 is then capped at the highest wait any process measured over that minute). `health` is evaluated on the aggregate.

An alert fires when the value is above its threshold. The latency thresholds are histogram bucket bounds, so a value at most the threshold never reads as above it.

| Alert | Warn | Critical | Meaning |
|---|---|---|---|
| `event_loop_p95_ms` (1 min, worst process) | > 100 ms | > 500 ms | The main thread is busy; every request waits behind it |
| `pool_wait_p95_ms` (1 min) | > 50 ms | > 1 s | Requests wait for a database connection |
| `pool_in_use_pct` (highest over 1 min, fullest pool) | > 90 % | | A pool is nearly full |
| `pool_failures_5m` | | > 0 | Requests got no connection and were answered 503 |
| `error_5xx_pct` (5 min, from 20 requests) | > 1 % | > 5 % | Server errors |
| `route_p95_ms:<route>` (5 min, from 20 requests on the route) | > 1 s | > 3 s | A slow route; AI, Netbox, import, export, bulk and CSV routes are left out |
| `rss_mb:<process>` | > 1024 MB | | Memory of one API process |

### PostgreSQL Settings
PostgreSQL ran on its defaults (128 MB shared buffers, 4 MB work memory; the step 0 bench of plan planning/perf-scale saw the amounts aggregate spill its sort to disk). Its configuration belongs to whoever runs the server (the host on QA and prod, the customer on premise), so KANAP ships a sizing script and applies nothing itself, except per-table autovacuum settings through a migration.
- **`infra/postgres/kanap-pg-tune.sh`** prints an include file sized from the host's memory, for a server shared with the KANAP containers or dedicated (`--dedicated`): `shared_buffers` 25 % of RAM dedicated, 15 % shared, 10 % shared under 6 GB (image builds on the same host need the room), at most 8 GB; `effective_cache_size` 75 % or 50 %; `work_mem` 8 MB under 6 GB, 16 MB up to 24 GB, 32 MB above; `maintenance_work_mem` 5 % between 64 MB and 1 GB; `random_page_cost = 1.1` and `effective_io_concurrency = 200` (SSD); `pg_stat_statements` with `track_io_timing`; `log_min_duration_statement = 500ms` with `log_parameter_max_length = 0`; `log_lock_waits`. The rule is in the script's header.
- **Statement statistics.** `shared_preload_libraries` is one list, and a value in an included file replaces the one in `postgresql.conf`: the script keeps the server's current libraries when given them (`--preload "$(psql -XAtc 'SHOW shared_preload_libraries')"`) and writes the line commented out otherwise. PostgreSQL does not start when a preloaded library is missing (RHEL and derivatives ship it in `postgresqlNN-contrib`): the script looks for `pg_stat_statements.so` on the host (`pg_config --pkglibdir`, then the usual package paths) and writes the line commented out when it is not there. A deploy then needs a PostgreSQL restart (for `shared_buffers` and the preload) and, once, `CREATE EXTENSION pg_stat_statements` in the KANAP database as a superuser.
- **Logged parameters.** A statement over 500 ms is logged with its bind parameters, which can carry personal data (names, e-mails, comment text): the script sets `log_parameter_max_length = 0` (PostgreSQL 13+), and the cloud servers should have the same before `log_min_duration_statement` is turned on there.
- **QA and prod**: nothing is applied by a deploy. QA has 3.8 GB shared with the containers and no swap: the shared rule gives 380 MB of shared buffers and 8 MB of work memory.
- **Autovacuum of the amounts** (migration `1853820000000`, the only setting a deploy applies): `spend_amounts` and `capex_amounts` are vacuumed after 2 % dead rows instead of 20 %, analysed after 1 % changed instead of 10 %, and on PostgreSQL 13+ vacuumed after 5 % inserted rows. No memory, no restart. A table the KANAP role does not own keeps its settings, and a table busy for more than 5 s (a running VACUUM holds the same lock) is skipped; both cases log the statement to run instead of failing the deploy.

It runs only while the task is enabled in the scheduled tasks: disabled, neither the start nor the cron syncs anything.
  - Refresh, while `TECHNOLOGY_CATALOG_SYNC_ENABLED`: the release cycles of endoflife.date (API v1, `GET /products/{product}`, one request a second, three tries on a failure of the service, a product read less than 20 hours ago skipped, the others left for the next run after two failures of the service in a row, an answer over 1 MB refused) for the entries some tenant adopted, into the platform cache `technology_catalog_products` (no `tenant_id`, like `vulnerability_cves`), with the rules of the script that builds the shipped file (`catalog/catalog-releases.ts`, checked against every shipped `cpe_version` by its spec). A cycle with a name or label that is blank or over 100 characters, or a date that is not a real day, is left out and logged; labels are cleaned in linear time. An entry may declare one CPE product per release (SQL Server, `a:microsoft:sql_server_{year}`; Windows Server, `o:microsoft:windows_server_{year}`, from the 2003 release): a release the cache adds brings it. A Windows Server version stores no patch level, so matching counts the whole release as concerned. The catalog's operating systems carry CPE identifiers. SUSE Linux Enterprise Server has none: the NVD keeps the service pack beside the version.
  - Living catalog: the shipped file with the cached cycles merged in (new cycles added, new dates on the shipped versions, which keep their label, `cpe_version` and build prefixes). A cached product counts only while the gate is on, when it was read after the day the shipped file was built (`source.retrieved_on`), and when it was read in the last 7 days; cached versions are checked again when read, so an adoption never fails on the cache.
  - Sync, in both modes and tenant by tenant (one transaction each, the technologies locked `FOR UPDATE`, each technology under a savepoint when the batch fails): each technology with a `catalog_key` receives the versions and the CPE identifiers it was never offered (with their dates and `technology_versions.catalog_key`, the provenance the record shows). An identifier is removed when `catalog_state.shipped_cpe` (the identifiers the shipped file listed at the previous pass, lower case) contains it, the shipped file no longer lists it, `catalog_state.cpe_written` contains it, and the technology still holds it (without case). `cpe_written` is what the catalog itself wrote and the tenant still holds, recalculated each pass as that intersection plus the identifiers added on the pass. A state without `cpe_written` withdraws nothing until the catalog writes one. An identifier the tenant typed before the catalog offered it, or already held on a technology that is adopted afterwards, never enters `cpe_written`. A state written before `shipped_cpe` withdraws nothing on this pass and records the shipped file's current identifiers. After the sync, `cpe_products` keeps an identifier the cache added (a release product) while the cache omits it, so a missing cache neither removes it nor offers it again, and keeps an identifier the tenant removed until the shipped file has been seen to drop it. An identifier the shipped file withdrew leaves that list, so a later offer adds it again. An identifier the tenant added, absent from the state, stays. A shipped file that lists no identifier, and whose entry is not marked `noCpe`, withdraws nothing: the pass logs it and keeps the previous `shipped_cpe`. An empty description the catalog never filled receives the catalog's short description in the tenant's language (`tenants.metadata.language`; without one, the language most of its enabled users chose in `users.locale`; else English), remembered in `catalog_state.description`, and `catalog_state.description_language` records that language. While the technology still holds that text, the same characters, a new description in that language replaces it, and `catalog_state.description` and the audit move only when that replacement is applied. A change of the tenant's language rewrites nothing. A state without `description_language` takes the language whose catalog text equals the remembered description, and is not rewritten when none does. A description the tenant changed stays. A description the catalog withdraws leaves the text in place. A version typed before with the same label (without case) and no `catalog_key` is attached instead, its empty values filled. On a version of the catalog, the end of standard support, the end of extended support and `cpe_version` follow the catalog while they still hold the value the catalog last wrote; an empty `cpe_version` is always completed; a date withdrawn upstream never erases one; a catalog date that would contradict the other date is the only value not applied (logged). `technologies.catalog_state` keeps the identifiers the catalog currently offers and, per version key, the values it last wrote: a value the tenant changed, a version or an identifier the tenant deleted stay as the tenant left them. One field of memory per technology was chosen over a provenance column per field: it also remembers deleted versions, which a column on the version row cannot. A technology without a usable state (adopted before C4, or an unreadable one) starts from the shipped file and what it holds of the catalog, all counted as offered; its empty values are completed, and nothing is removed on that pass (the state cannot tell an identifier the shipped catalog withdrew from one the tenant added). A run with any failure (a product not read, a technology not synced) ends as a failed run in the scheduled tasks, once everything else is done.

- **Knowledge and web sources** are configured per agent on its scope policy, distinct from tenant-wide AI settings. The policy selects KANAP knowledge (all readable libraries or a subset, always intersected with the configuring admin's readable libraries) and whether the agent may search the web. Internal knowledge takes precedence; web results carry `external` trust and are cited with their URL.
- **`web_search`** is a governed internal capability (provider kind `web`, internal surface, read effect, autonomy `A1`, no approval, not exposed over MCP). Its handler uses `BraveSearchService`, which strips UUIDs, internal references, emails and internal hostnames from the query and refuses to run if nothing public remains. Dispatch is gated on `AI_WEB_SEARCH_READY` and is best-effort.
- **Model registry**: models are rows in `ai_model_configs` per tenant (provider `anthropic|openai|ollama|custom`, model, endpoint, encrypted key, vision support, EUR prices per million tokens, timeout). Chat (`ai_settings.chat_model_config_id`) and agents (`ai_agent_definitions.llm_model_config_id`) reference a config; `null` resolves to the tenant default, then (multi-tenant only) to the platform built-in model configured by platform admins (`platform_ai_config`, `platform_ai_plan_limits`), once the workspace has confirmed it (next bullet). `AiModelResolverService` is the single resolution point for chat, agents, ingestion and the fallback after a model is archived. The flat `ai_settings.llm_*` columns are deprecated. Usage is metered in `ai_builtin_usage`.
- **Included model confirmation** (multi-tenant only; single-tenant has no included model, the new columns stay empty and nothing changes). Before any workspace data reaches the platform built-in model, an administrator of the workspace confirms the provider shown and where it is processed.
  - *Identity.* `platform_ai_config.disclosure_name` (1 to 80 characters) and `disclosure_location` (ISO 3166-1 alpha-2 code in upper case, or `EU`) are what the platform console labels "Provider name shown to customers" and "Where data is processed". Both columns are nullable. The identity key is `builtinProviderKey` = `provider|endpoint host|name|location` (`ai/platform/platform-ai-config.service.ts`): a change of technical provider or endpoint host, of the name or of the location produces a new key, a change of model alone does not. While the name or the location is empty the identity is null and the included model counts as not configured. The platform console refuses a change of provider or endpoint host unless the name and the location are sent in the same save, and asks for a confirmation in the UI when it will make workspaces confirm again. The migration (`1853885000000`) adds the columns and pre-fills Anthropic / `US` when the platform row calls the Anthropic API directly (provider `anthropic`, no endpoint or `api.anthropic.com`); any other setup stays empty with a warning. It writes nothing in tenant tables.
  - *Acceptance.* `ai_settings.builtin_accepted_key`, `builtin_accepted_at` and `builtin_accepted_by` (nullable text, timestamptz, uuid) hold the workspace's confirmation. It is valid only while `builtin_accepted_key` equals the platform's current key. `PATCH /ai/settings` takes `accept_builtin_provider_key` (the key shown in the settings view; `null` withdraws). A key that is not the current one is refused with `400` `BUILTIN_PROVIDER_CHANGED` and the current identity in `builtin_provider`. Turning the assistant on (`chat_enabled: true`) while the included model is unconfirmed is refused with `400` `BUILTIN_PROVIDER_CONFIRMATION_REQUIRED` and the identity to confirm; the UI resends the same payload together with the key. Other changes save while the assistant waits. Changes go through the usual `ai_settings` audit entry (before and after views).
  - *Gate.* In the built-in branch of the resolver, one `getBuiltinRuntime()` read of the platform record supplies both the identity compared with the workspace's key and the runtime that is called. A mismatch fails with `builtin_not_accepted`. Callers that send nothing to the included model pass `includedModelGate: 'none'`: the MCP access check and message budget, and the agents' tool context. The settings view, `GET /ai/capabilities` (chat reason `builtin_not_accepted`, flag `builtin_confirmation_needed` when an enabled agent falls back on the unconfirmed model) and the agent quota gate (`AiAgentBuiltinQuotaService`: the scheduled poller pauses, a manual run fails, nothing is consumed) all read the same readiness. An agent or the assistant on a registry model is never gated.
  - *View.* `GET /ai/settings` returns `builtin_provider` (`in_use`, `used_by_assistant`, `name`, `location`, `key`, `accepted`, `accepted_at`, `accepted_by_name`). The platform config view (`GET /admin/ai/config`, `PATCH /admin/ai/config`) carries `disclosure_name`, `disclosure_location` and the derived `disclosure_key`.
- **Chat and MCP**: native chat is served at `/ai/chat` (`ai_conversations`, `ai_messages`, attachments, retention job). An inbound MCP server (`POST /ai/mcp`, JSON-RPC, server name `kanap-mcp`) exposes the MCP-enabled capability contracts to external clients, authenticated by tenant-scoped API keys (`ai_api_keys`, `Authorization: Bearer kanap_mcp_…` or `X-API-Key`) or by OAuth access tokens (next item), with access policy, rate limiting (60 requests a minute per key or grant by default) and an audit trail (`backend/src/ai/control-plane/mcp/`). Keys are created through `POST /ai/keys` (`ai_mcp:reader`), but the only UI is the admin Plaid settings page (`ai_settings:admin`), so in practice keys belong to settings admins and read with their access.
- **MCP OAuth** (`backend/src/ai/oauth/`): MCP clients such as Claude connect without an API key. The tenant's address is both the authorization server (issuer `https://<slug>.kanap.net`) and the protected resource (`<issuer>/api/ai/mcp`). Discovery: `GET /.well-known/oauth-protected-resource/api/ai/mcp` (and the root form, RFC 9728) and `GET /.well-known/oauth-authorization-server` (RFC 8414), routed to the API by nginx (`location ^~ /.well-known/oauth-`). Clients identify with a Client ID Metadata Document (an https `client_id` URL on port 443): it is fetched only for a signed-in user, with the SSRF guard and no operator allowlist, pinned addresses, names resolved by c-ares (off the threadpool), no redirect, 5 s, 16 KB, at most 6 fetches at once per process, cached 1 h (failures 1 min), and one generic error. `GET /oauth/authorize` checks only that `client_id` and `redirect_uri` are usable (at most 512 characters each) and sends every request to the web app's page `/oauth/authorize`, never to the client. The page reads `GET /oauth/authorize/request`, which validates everything (CIMD redirect URI, loopback on any port; PKCE S256; `resource`, RFC 8707; `offline_access` ignored) and returns the consent details (`remembered` when the user has a live grant for this client, marked to be remembered, with the same redirect host; `auto_approve` when it is remembered and the redirect is a loopback one, since a web redirect always takes a click on the screen) or the error, with `redirect_to` back to the client once its redirect URI is verified. The page posts `POST /oauth/authorize/decision` under the web session; a refusal is the sign-in event `mcp_connection_refused`. `POST /oauth/token` (form-encoded, rate limit per address and tenant) exchanges the code and refreshes; `POST /oauth/revoke` follows RFC 7009. Each grant is an `ai_api_keys` row with `credential_kind = 'oauth'` (client id, name, redirect URI, the code's `jti`, unique per tenant, `oauth_remember`), so policy, rate limit, revocation and audit are the key's; a user keeps at most 5 live grants per client, the oldest is retired. The code (60 s) and the access token (15 min, `aud` = the MCP URL, claim `grant` = the row, accepted in `Authorization: Bearer` only) are JWTs of their own families. `key_hash` holds the current refresh token (`kanap_mcprt_…`, 90 days sliding, capped by the key max lifetime). Each refresh rotates it to a successor derived from the presented token: the token just replaced, presented again within a minute (a lost answer, two refreshes at once), gets that same successor; an older genuine token revokes the grant, as does a reused code. A refresh checks the grant and its owner only (MCP access itself is checked on every MCP request); one `refreshed` audit row per grant and hour at most. Without a credential, `/ai/mcp` answers 401 with `WWW-Authenticate: Bearer resource_metadata="…", scope="mcp:read"`. In development, connect through `<slug>.lvh.me` or the tunnel: the `*.localhost` proxy rewrites the host.
- **Subscription gate**: on frozen or trial-expired tenants every AI feature is off (chat, MCP, agents, scheduled ingestion). `evaluateSubscriptionAccess` in `backend/src/billing/subscription-freeze.util.ts` is the single decision point; it is a no-op when Stripe is not configured, so on-premise is unaffected.
- See `doc/plaid-architecture.md` for the full control-plane design (runs/steps/tool executions, capability registry, approval service, automation catalog, live-readiness harness).

### Scheduled Tasks
- All recurring work registers with `ScheduledTasksService` (`backend/src/admin/scheduled-tasks/`) at module init. There are no `@Cron` decorators left. Each task has a default cron, an override stored in the global `scheduled_tasks` table (editable from the admin console) and a run log in `scheduled_task_runs`.
- Registered tasks include expiration warnings (`check-expirations`, daily 08:00 UTC), weekly review digests (`send-weekly-reviews`, hourly), Entra directory sync (daily 03:00 UTC), ticket and alert ingestion for agents, approval lifecycle sweeping, agent activity and conversation retention, mutation preview expiration, search index reindex, orphaned attachment and ghost object cleanup, the renewal decision tasks of contracts (`contract-renewal-tasks`, daily 07:30 UTC, see Contract Renewal Decision), and the retention of sign-in events (`auth-event-retention`, daily 03:40 UTC, one transaction per tenant: `audit_log` rows with `table_name = 'auth'` older than 365 days).
- Every API process schedules every enabled task. A cron tick runs in one process only: the process that moves `scheduled_tasks.last_tick_at` to the tick's scheduled time runs the task, the others skip (`claimTick`); a stored tick more than a day ahead is claimed over, with a warning. The same claim checks the stored cron and `enabled`, so a change made in the admin console, which reaches one process, makes the others reschedule or drop their job at their next tick. `executeTask` then takes the task's session advisory lock and releases it on one dedicated connection, so a run that overlaps another run of the same task (a long run, a manual trigger) is skipped. At a stop no run starts any more, the running ones get the drain time, and one still going is recorded as interrupted. A task registered with `runOnStartup` also runs once when the API server starts: `main.ts` calls `runStartupTasks()` after `listen`, in the lead process only (the single process, or worker 1), so scripts and specs that build an AppModule context never run it.
- `lifecycle-status-sync` (hourly, and once at server start) sets the stored `status` from `disabled_at` on the twelve tables where the status is derived from the end of validity (`LIFECYCLE_STATUS_TABLES` in `backend/src/cleanup/lifecycle-status-sync.service.ts`, checked against the catalog by its spec). One short transaction per table and tenant with a 500 ms lock timeout: a table whose row is locked by an edit is skipped until the next run. Frozen tenants included, both deployment modes. Only `status` changes: no audit row, `updated_at` kept, no line's `row_version` bumped (its trigger ignores `status`). Without it, a future end of validity that passes leaves the stored value stale until the next edit. The status-change emails (CAPEX, OPEX, contracts) take the status before an edit from the stored end of validity, so they never depend on this task having run.

## Multitenancy
- Storage model: single Postgres database per environment (not per-tenant). Tenants share tables keyed by `tenant_id`. See `doc/adr/0002-multitenancy-storage.md`.
- Isolation: RLS on all multi-tenant tables; the API sets a request-scoped session variable (`set_config('app.current_tenant', '<uuid>', true)`) used by the policies. Two canonicalization migrations (`1844300000000`, `1844400000000`) repaired earlier drift and enforce `FORCE ROW LEVEL SECURITY` everywhere. Policies exist in two equivalent forms: `tenant_id = app_current_tenant()` (most tables) and the older `tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid` (about a quarter, `portfolio_projects` included). `app_current_tenant()` is that same expression with no fallback: without context it returns NULL, so both forms filter out every row and inserts fail on `NOT NULL`.
- Indexing: lead with `tenant_id` in composite keys and uniques (`PRIMARY KEY (tenant_id, id)`, `UNIQUE (tenant_id, slug)`).
- Tenancy resolution (`backend/src/common/tenancy/request-tenancy.middleware.ts`, mounted by `backend/src/http-app.ts`): apex hosts (`kanap.net`, `www.`, `dev.`, `qa.`, `*.lvh.me`) are no-tenant public hosts; `<slug>.<domain>` resolves a `Tenant` by slug (404 `TENANT_NOT_FOUND` with a marketing redirect otherwise); `PLATFORM_ADMIN_HOST` binds the `platform-admin` system tenant. In single-tenant mode Host parsing is skipped and `DEFAULT_TENANT_SLUG` is used (503 `TENANT_NOT_READY` until provisioned).
- Sessions: cookies are scoped per subdomain; no cross-subdomain cookies.
- Scalability: several API processes per container (`API_WORKERS`, see [Several API Processes](#several-api-processes)); PgBouncer past about 80 connections, after the session-state changes listed in [Database Pool](#database-pool); partition large tables by `tenant_id` if needed.
- Provisioning flow (cloud only): marketing POSTs to `/api/public/start-trial` (`org`, `slug`, `email`, required `country_iso`, `captchaToken`). The API verifies Turnstile (`off|monitor|enforce`, production defaults to `enforce`), records the request in `trial_signups`, emails an activation link, and `/api/public/activate-trial` provisions the tenant, its Administrator, an initial company from `country_iso` and a local trialing subscription, then returns a password-reset token so the admin sets credentials inside the tenant app.
- Tenant slug reservation policy is centralized in `backend/src/tenants/tenant-slug-policy.ts` and enforced in `POST /public/start-trial` and `TenantsService.createTenant`/`updateTenant`. Unavailable slugs return `400` with code `SUBDOMAIN_NOT_AVAILABLE`.
- Default CoA provisioning: during activation, after `app.current_tenant` is set, the API looks for the single global platform CoA template marked `loaded_by_default` and, when present, copies it into a `GLOBAL` CoA marked as the tenant's Global Default. The initial company auto-assigns to its country's default CoA when one exists, else to the Global Default.
- Tenant branding is stored on `tenants.branding` (jsonb: logo path/version, light/dark primary colors, dark-mode logo toggle). The column sits on the tenant record (no per-table `tenant_id`) and is guarded by host + permission checks in code.
- Activity comment notifications: rich-text comment bodies are sanitized before email rendering; inline images are embedded as CID attachments when possible, with absolute URL fallback.

### Contract Terms
- One module dates a contract's terms: `backend/src/contracts/contract-terms.ts`, with the TypeScript function (`computeContractTerms`, used for the API responses) and the same values as SQL (`contractTermsSql`, used by the list's sort and filters, the AI registry and the expiry warnings). Nothing else computes an end date or a cancellation deadline. Terms are computed on the fly, never stored.
- A contract runs in successive terms of `duration_months` months from `start_date`: term `k` is `[start + k·duration months, start + (k+1)·duration months − 1 day]`. With `auto_renewal` the terms go on without limit. An end of validity (`disabled_at`, its UTC day) stops them: no term starts after it. Without `auto_renewal`, a contract with an end of validity runs in terms up to it, its past terms counted (`term_index`, `renewed`, commitments, states: lot CR2, round 2, so turning the renewal off keeps the history); without one, it has only its first term. A duration of 0 is a single term of no length. A term's cancellation deadline is its end minus `notice_period_months` months (it may fall before the term starts when the notice is as long as the term).
- Months follow PostgreSQL's `date + interval 'N months'`: same day of the month, brought back to the month's last day when it does not exist (31 January + 1 month = 28 February; 31 December − 3 months = 30 September), in TypeScript and SQL alike.
- Values as of today (UTC calendar day): `term_index` (0 for the first term), `renewed` (`term_index > 0`), `current_term_end` (end of the term containing today; the first term for a future contract, the last one once the contract has ended), `next_cancellation_deadline` (first deadline on or after today among the terms that exist; null when there is none or when it falls after the end of validity). `end_date` equals `current_term_end`; `cancellation_deadline` equals `next_cancellation_deadline`, or the last term's deadline when that is null.
- The contract list adds two values from the same module. `next_due_date`: the next cancellation deadline of a contract that renews at the end of its current term (its term end when no deadline remains); the end of any other contract (its term end, or its end of validity when that comes first); null once that end has passed. `term_state`, the first that applies: `expired` (no next due date); in the last term, `to_decide` for a contract without `auto_renewal` whose end (term end or end of validity) is within the tenant's decision window from today while no decision to let it end (`end`, `terminate`) is recorded for that term, `ending` otherwise; `to_decide` for a contract with `auto_renewal` whose next cancellation deadline is within the window while no renewal is confirmed for the term of that deadline (see Contract Renewal Decision); `renewed` (the current term's deadline has passed: the contract goes on into the next term), `in_progress`. The list sorts on `next_due_date` by default, ended contracts last in both directions.
- `GET /contracts/totals` sums the yearly amounts of the contracts a list request selects in the tenant's reporting currency, with the year's latest rate set (the one the budget's live columns use). A currency that set does not rate stays out of the sum and is reported by currency (`excluded`), never counted at 1. With a budget year and column it also sums the budget coverage (see Contract Commitments and Budget Coverage).
- Expiry warnings (`checkContractExpirationsForTenant`, schedule 30/14/7/1 days): every contract is warned on its next cancellation deadline; a contract is warned on its term end only when no term follows it (no renewal, or an end of validity before the next term starts).
- `contract-terms.spec.ts` checks the TypeScript rule on hand-worked cases and against the frontend copy (`frontend/src/pages/contracts/contractTerms.ts`, used by the details form while the user edits); `contract-terms.parity.spec.ts` checks the SQL on the same cases and on a sweep of month-end combinations (the list's `next_due_date` and `term_state` included; the frontend copy does not compute them).

### Contract Renewal Decision
- **Decision window** (`backend/src/contracts/contract-settings.service.ts`): a tenant setting, `tenants.metadata.contracts.decision_window_days`, whole days from 0 to 365, default 90 (`CONTRACT_DECISION_WINDOW_DAYS`). No table: it lives in the tenant metadata like the budget column names, written under the tenant row lock (key only) with an audit row on `tenants`; a tenant reset gives the default back. `GET /contract-settings` (contracts reader), `PATCH /contract-settings` (contracts admin; 400 out of range). Every reader of the window takes it from there: the list's `term_state` (values, filter, sort) and the `to_decide` count of `GET /contracts/totals` (which also answers `decision_window_days` for the quick filter label), `GET /contracts/:id` (`term_state`, and `decision_window_days` for the window drawn on the timeline), the decision box and the daily run. `contractTermsSql` and `computeContractTerms` take it as `decisionWindowDays`; the AI registry reads no state, and the dashboard tile sorts on `next_due_date`, which does not depend on it.
- **The term decided** (`contract-renewal.ts`, pure): on the calendar of the contract renewing with no end (`contractTermCalendar` in `contract-terms.ts`), the term of the first cancellation deadline on or after today (`pending`), and the term containing today when its own deadline has passed (`current`, whose decision shows until its end). A decision is keyed by the last day of its term (`term_end`): a change of the notice keeps it, a change of the start date or the duration leaves it behind.
- **No table**: the contract's audit rows hold everything (`table_name = 'contracts'`, `record_id` the contract, `source_ref = 'contract-renewal:<term_end>'`, read through `idx_audit_log_tenant_record_created`, on `(tenant_id, record_id, created_at)`). `after_json.renewal_task = { task_id, item_number, term_end, deadline }`: the task the run created (user null, source `system`). `after_json.renewal_decision = { decision, reason, term_end, deadline, task_id, previous_disabled_at? }` beside the contract's columns (`before_json` the contract before): `renew`, `terminate`, `renegotiate` or `undo`, the latest one counting.
- **End decision** (lot CR2, round 2; `mode = 'end'`): a contract without `auto_renewal` whose end (`renewalEnd`: its end of validity, or its first term's end without one) falls within the window awaits a decision on that end, keyed by the term that contains it: renew (`auto_renewal` on, end of validity removed, `previous_auto_renewal` and `previous_disabled_at` kept, undoable until that end) or let it end (`end`, contract unchanged, undoable while it has not ended). A termination recorded on that term counts as letting it end. The decision box titles it "Ends on … · decision due"; the timeline's sentence adds "decision due" with the orange dot; the list counts it in "to decide" until decided. The daily run creates its task: "Decide whether to renew or let <contract> end", due on the end, same idempotence key. `POST /contracts/:id/renewal/end` (`contracts:member`).
- **State** (`resolveRenewalState`, `mode = 'renewal'` for a contract with `auto_renewal`): `decided` when the latest decision for the pending term stands (a renewal while the contract still renews after it; a termination while its end of validity is still the term's last day), undoable; otherwise `pending` when the contract renews after that term and the deadline falls within the window (`renegotiating` after a renegotiation); otherwise `decided`, not undoable, when a decision stands for the current term; otherwise `none`. A change by hand of the renewal or the end of validity voids a decision that no longer matches.
- **Termination** (lot CR2, round 2): it turns `auto_renewal` off (the term rule keeps the terms of a contract without renewal up to its end of validity) and sets the end of validity (noon UTC, as a date typed in the UI) to the day chosen, `end_date` (lot CR2, round 1): by default the proposed end (`proposedEndDate`: the last day of the first term whose cancellation deadline has not passed, today included, which is the term decided), any day from today (UTC) and from the contract's start otherwise (`checkEndDate`, 400 for anything else); an earlier day than the proposed one is allowed, the page warns that it must be agreed with the supplier. The decision is keyed by the term that contains the end chosen, where the contract, now without renewal, looks for its end decision, and keeps `end_date`, `previous_auto_renewal` and `previous_disabled_at`; it stands while the end of validity is still that day; the contract then reads `ending`, its commitments and its budget coverage stop at that day, the expiry warnings name its end (the end of validity, when it comes before the term end). The undoing puts both previous values back while the deadline has not passed. Terminations recorded before this round kept `auto_renewal` on; they still stand.
- **Daily run** (`ContractRenewalService.run`, scheduled task `contract-renewal-tasks`, daily 07:30 UTC): every active tenant, one transaction each; a frozen or trial-expired subscription is skipped (no-op on-premise, as the Netbox sync). Candidates: contracts with `term_state = 'to_decide'` under the tenant's window and no past end of validity. For each, the contract row is locked (`FOR NO KEY UPDATE`), then its audit rows are read: a pending decision with no `renewal_task` row for its term gets a task (`TasksUnifiedService.createForTarget`, `related_object_type = 'contract'`, title "Decide on the renewal of <contract>" in the owner's language, or in the tenant's (`tenants.metadata.language`) when the owner never chose one, then English, due on the deadline, assigned to the owner, the usual assignment e-mail, audit source `system` with the same `source_ref`) and the `renewal_task` row. One task per contract and term: a second run, or one waiting on the row lock, finds the row; a deleted task is not created again. A run missed for days creates the task on the next one while the deadline has not passed. No enabled owner: no task (the summary counts them; the task comes on a later run once an owner is set). A contract without tacit renewal never awaits a decision.
- **Actions** (`ContractRenewalController`, `contracts:member`, one route each: `POST /contracts/:id/renewal/renew|terminate|renegotiate|undo`, body `{ reason? }`, cut at 2 000 characters): in the request transaction, the contract row is locked, the state read again, then the contract (termination and its undoing only), the audit row, and the task through `TaskActivitiesService.createUnified` (the justification as a comment; done on a renewal or a termination, open again on an undo; a renegotiation keeps its status). `renew`, `terminate` and `renegotiate` need a decision awaited, `undo` an undoable one: 409 otherwise. A contract of another tenant is a 404. `GET /contracts/:id/renewal` (`contracts:reader`) answers the box: `state`, `term` with `days_left`, the decision with its author, `can_undo`, the task (`T-n`, status, assignee) and, while pending, what a termination changes (`impact`: the commitments of the term's year and the next one before and after, in the contract's currency; the applications linked to the contract; the assets whose support contract it is, `asset_support_info.support_contract_id`).
- **A renewal confirmed leaves "to decide"** (lot CR2): a contract whose latest decision for the term of its next cancellation deadline is `renew` is not `to_decide` for that term (it reads `in_progress`, or `renewed` when the current term's deadline has passed); its next term's deadline brings it back into the window. The term rule takes the confirmed terms as `renewalConfirmed`, a test on a term's last day: in SQL, `renewalConfirmedSql('c')` (`contract-renewal.ts`) reads the latest decision row of that term for the row's contract, correlated, and only for a contract whose next deadline is within the window; in TypeScript, `readConfirmedRenewals` reads the page's contracts in one query (`record_id = ANY($1)`, latest row per contract and term) and `confirmedRenewalOf` hands one contract's set to `contractTermFields`. Same state everywhere: the list's value, its `term_state` filter and the ids behind it, the `to_decide` count of the totals, the compliance register export filtered on the state, and `GET /contracts/:id`. The daily run keeps the plain state for its candidates (the decision box state skips a decided contract). An undoing or a renegotiation after the renewal makes it `to_decide` again. The parity spec checks the term the option is asked about on its own cases and on the whole sweep. The contract page draws the confirmation from `GET /contracts/:id/renewal`: "Renewal confirmed · next term from … to …", no deadline marker nor window for the term decided, the next term drawn as one that will run.
- **Turning the renewal off** (lot CR2, round 2): `PATCH /contracts/:id` refuses (400) to turn off `auto_renewal` on a contract past its first term when the contract is left without an end of validity (`turnsOffRenewalOfRenewedContract`: the term rule would drop the terms it has run); with an end of validity in the same request (or already there), it is allowed and the history stays. The AI mutations go through the same `update`; the CSV import (which has no end of validity column) reports the row before it writes anything, dry run included. The contract page asks first: "No" in the renewal field of a contract already renewed, or of any contract awaiting a renewal decision, opens "Turn off the tacit renewal" with the end to choose (proposed end, notice, warning before it, consequences for the day chosen through `GET /contracts/:id/renewal?end_date=`) and "The contract will end on …, unless renewed". Confirming calls `POST /contracts/:id/renewal/stop` (`contracts:member`, `ContractRenewalService.stopRenewal`, body `{ end_date? }`, checked as for a termination): under the row lock, `auto_renewal` off and the end of validity on that day (noon UTC), one audit row (`after_json.renewal_stop.end_date`). It is no termination and records no decision: the contract now awaits one on its end. The decision task open for it (the one of the pending term, or of the end) is adapted: title "Decide whether to renew or let <contract> end" in its assignee's language, then the user's, then the tenant's, due on the end, a comment saying why in the user's language, then the tenant's, and a `renewal_task` row under the end's key so the run creates no other; without one, a task is created when the end falls within the window. 409 when the renewal is already off, or when the contract is in its first term with no decision awaited (the field turns it off directly there). It answers the decision box's body.
- **Turning the renewal back on** (lot CR2, round 3): "Yes" in the renewal field of a contract without renewal that has an end of validity (set by turning the renewal off, or by the lifecycle: no distinction) opens "Turn the tacit renewal back on": "The contract will renew tacitly and the end on … will be removed." Confirming calls `POST /contracts/:id/renewal/resume` (`contracts:member`, `ContractRenewalService.resumeRenewal`): under the row lock, `auto_renewal` on and the end of validity removed in one write. While a decision is awaited on its end (`end` mode), it is that decision's renew (decision recorded, task closed, undoable). Otherwise one audit row (`after_json.renewal_resume.previous_end_date`), and the decision task still open on the end follows: when the renewal decision is now due (its deadline within the window), it becomes that decision's task again (title "Decide on the renewal of …" in the assignee's language, then the user's, then the tenant's, due on the cancellation deadline, `renewal_task` row under that term's key, the run creates no other); otherwise it is closed. Either way a comment says why ("Tacit renewal turned back on: the end on … is removed."), in the user's language, then the tenant's. 409 when the renewal is already on, or without an end of validity (the field turns it on directly there).
- Specs: `contract-renewal.spec.ts` (the rule, the setting's bounds, the route rights), `contract-renewal.integration.spec.ts` (the run, the owner's language, the window everywhere, each action and its undoing, a confirmed renewal out of "to decide" everywhere, the edit, import and stop of a renewed contract, another tenant), `contract-terms.spec.ts` and `contract-terms.parity.spec.ts` (`renewalConfirmed`, `turnsOffRenewalOfRenewedContract`).

### Contract Commitments and Budget Coverage
- **Commitment of a year** (`contract-terms.ts`: `contractCommitmentCents`, `contractCommitmentSql`): the yearly amount at signature prorated over the months of the year covered by a term, a month covered in part by the share of its days covered. The terms cover one span from `start_date`: every term with `auto_renewal` (projected with no end) or with an end of validity, the first term only without either, nothing after the end of validity. No indexation: the amount at signature holds for every term. Exact arithmetic: a day of any month is a whole number of units of `MONTH_SHARE_UNITS` (377 580, the least common multiple of 28 to 31), and the commitment in cents is `annual cents × covered units / (12 × 377 580)`, rounded half away from zero once. The parity spec checks the SQL against the TypeScript on hand-worked cases (SAP renewed every July: 350 000 a year; ended on 30 June 2027: 175 000 in 2027 and 0 in 2028; a contract starting on the 15th; no renewal and an end on 31 March 2027: 225 000) and on a sweep. The API alone computes it; the frontend has no copy.
- **Budget coverage** (`backend/src/contracts/contract-budget.ts`), for a year and one of the five budget columns the user picks: `committed` (the commitment converted to the reporting currency with the year's latest rate set, `contractFxRates`, the conversion of the list's footer; null when the currency has no rate that year, 0 when nothing is committed), `linked` (the sum of the linked lines' amounts in that year and column), `gap` (`linked − committed`) and `state`, the first that applies: `no_commitment` (nothing committed, no linked line with an amount), `not_started` (no budget line of the tenant has an amount in that year and column), `no_line` (no linked line with an amount), `under` (linked below committed), `over` (linked above committed by more than `CONTRACT_BUDGET_OVER_PERCENT` = 10 %), `covered`. No rule reads a column's name or rank.
- **The lines' amounts are the budget list's own**: `budgetListAmountsByIds` (`spend/budget-list/budget-list.service.ts`) reads the list engine's field of each amount key (`y2027Budget`) for a batch of line ids in one statement, with no lifecycle scope: the same conversion (rates of each version's set or the live set) and the same mask after a line's end of validity as the budget list and its footer.
- **One statement** (`contractBudgetSql`) gives these values for every contract of the tenant and each year asked for. Its inputs are read first, in a fixed number of statements whatever the number of contracts (`loadContractBudgetInputs`): the linked lines' amounts by batch of ids, the years with budget data in the column, the rates of the contracts' currencies. The contract list joins it as a materialized CTE (`cb`) to sort, filter and total on the figures; the contract page reads it for one contract and every year the selector offers (the year before the current one when the budget holds lines for it, the current year and the two after).
- **A linked line without a rate**: `budgetListAmountsByIds` answers null for an amount whose line currency has no rate that year. `loadContractBudgetInputs` reads it again in the line's currency (`local_` key): 0 is a known 0, anything else stays null (`lineFxMissing`). The line is left out of `linked`, the contract's row carries `linked_fx_missing`, and its gap and state are null (unknown, never `covered` or `over`). The Budget tab and the list footer name those lines by currency and year (`lines_fx_missing`, `linked_fx_missing`).
- **Access**: the figures need the `budget` reader right (or an administrator) besides `contracts` reader: the list ignores `budget_year` / `budget_column` without it, `GET /contracts/:id/budget` answers 403.
- `contract-budget.integration.spec.ts`: the lines' amounts against the budget list's rows and footer (a USD line, a line past its end of validity), every state, the sort and filters on the server, the totals and their quick filter counts, the contract page's years, a currency without a rate, another tenant's data never read.

### Contract Compliance Register
- **What it is** (`backend/src/contracts/contract-compliance.ts`): for each contract, the requirements it is expected to hold and what the user recorded. The screen helps keep a register; it makes no claim about regulatory compliance.
- **Requirements**: a fixed list in v1, stable codes (`gdpr_dpa`, `data_location`, `reversibility`, `exit_plan`, `audit_security`), labels in the locale files (`contracts.compliance.requirements.*`) and in the register's words. `contract_compliance_items.requirement` is a text code with no check constraint against the list, so a list per tenant can come later without a migration (the codes would then come from the tenant's settings instead of the constant).
- **Expected**: computed on the fly, never stored. The applications a contract covers are those linked to it (`application_contracts`) and those with an instance on an asset it covers (`asset_contracts`, or `asset_support_info.support_contract_id`); an application past its end of validity counts no more. Rules, each with its reason: personal data (`applications.contains_pii`) makes `gdpr_dpa` and `data_location` expected; a high business or cyber criticality makes `reversibility`, `exit_plan` and `audit_security` expected; an instance on an asset whose location's hosting type is in the cloud makes `data_location` expected. High: the two most severe levels of the tenant's catalog by rank (the most severe alone below three levels), whatever their codes (`business_critical` and `high`, `critical` and `high` with the defaults). Cloud: the hosting type's category in the IT operations settings (`public_cloud`, `private_cloud`, `saas` by default; a type without category is on premises only for `on_prem` and `colocation`).
- **Recorded**: `contract_compliance_items` (state `present`, `absent` or `not_applicable`, a reference of at most 500 characters, `updated_by`, `updated_at`). A requirement with neither state nor reference has no row. A write locks the contract's row first and writes one audit row per change.
- **Summary**: `expected`, `missing` (expected and recorded absent), `to_check` (expected, no state) and `state`: `missing`, else `to_check`, else `complete`; `none` when nothing is expected. A requirement not expected never counts. The contract page's Compliance tab shows `missing` as its badge.
- **The list**: each page's summaries come from one statement by batch of ids (`complianceSummarySql`). Sorting or filtering on `compliance_state` joins the same statement for every contract of the tenant as a materialized CTE (`cc`), and only then. The settings the rules read (catalogs, hosting categories) are read once per request from `tenants.metadata.it_ops`.
- **The register** (CSV, `GET /contracts/compliance-register/export`): the contracts of a list request, one line per contract and requirement, in the screen's language. Three statements whatever the number of contracts.
- `contract-compliance.spec.ts` (high levels, hosting categories, summary, reasons in words), `contract-compliance.integration.spec.ts` (the rules through links and assets, recording and its audit, the list's sort, filter and totals against the tab's summary, the register, another tenant), `contract-compliance-migration.integration.spec.ts` (shape, rerun, down and up on a database with and without contracts).

#### Internal tenants
An internal tenant is a demonstration or test tenant that runs with no money flow. A platform administrator marks it from the tenant detail in the platform console ("Mark as internal tenant"), which calls `POST /admin/tenants/:id/mark-internal`.

### Request DB Context
- A global guard (`TenantInitGuard`) opens a per-request QueryRunner transaction and sets the tenant GUC before any other guard, so permission checks already run under RLS. A global interceptor (`TenantInterceptor`) reuses the transaction for the handler, commits it before the handler's value goes out (a failed commit answers 500, unless a handler that writes the response itself has already answered), and rolls it back before a handler error reaches the exception filter. Both release the connection on error. Opt-outs: `@Public()` and `@SkipTenantTransaction()`.
- Controllers pass the request `EntityManager` (`req.queryRunner.manager`) into services so every query runs in the tenant-scoped session.
- **Bounded waits** (`backend/src/common/request-db-timeouts.ts`): the statement that sets the tenant also sets, transaction-local, `lock_timeout` 5 s, `statement_timeout` 30 s and `idle_in_transaction_session_timeout` 60 s (env `DB_LOCK_TIMEOUT_MS`, `DB_STATEMENT_TIMEOUT_MS`, `DB_IDLE_IN_TRANSACTION_TIMEOUT_MS`, milliseconds, 0 = no limit). `@LongRunningRequest(...)` raises them on a route, never lowers them: `BULK_WRITE_TIMEOUTS` (30 s / 2 min / 5 min) on CSV imports, budget column copy and clear, allocation copy, master-data year copy, freeze/unfreeze and bulk delete of budget lines; `OUTSIDE_WORK_TIMEOUTS` (idle 10 min) on Netbox, Entra directory sync, document exports, the platform AI provider test and Stripe calls; `TENANT_PURGE_TIMEOUTS` (idle 30 min) on tenant deletion. Every `multipart/form-data` request (a file upload) gets the 10 min idle limit too: the guard opens the transaction before the route's `FileInterceptor` reads the body, so a slow upload counts as idle in transaction. The waits are kept on the request (`req._requestDbTimeouts`) so a runner reopened mid-request (`import-connection.ts`, an import that gives its connection back) gets the same ones. Work that waits on an outside service and does not need the transaction meanwhile gives the connection back first: an import reopens a transaction after it (`createRequestReleaseConnection`); the user invitation commits its token and status, sends its e-mail and queries nothing after (`createRequestCommitThenRun`). Either refuses to go on (503 `busy`) when the request's connection was already lost.
- **Database errors** (`backend/src/common/filters/database-error.mapping.ts`, applied by `ReleaseTenantRunnerFilter` after its rollback and release): 23505 → 409 `duplicate`, 23503 → 409 `parent_gone` (or `in_use` for a refused DELETE), 40P01 / 40001 → 409 `retry`, 55P03 / 57014 / 25P03 → 503 `busy` with `Retry-After: 2` (a fixed 2 s, whatever the cause). Not a database error but in the same family: 409 `operation_running`, a bulk budget operation refused while another one of the tenant runs (`budget-locks.ts`); a client does not retry it by itself. The body carries the `code` (the frontend translates `errors:<code>`) and a plain-language message; one `[db]` warning line is logged instead of a stack trace, naming the SQLSTATE, the table and the constraint, never the driver's `detail` (it quotes row values).
- **Lost or missing connection**: no connection from the pool after the tenant lookup (`connectRequestRunner` in the guard and the interceptor: pool timeout, database unreachable) and a connection that ended while the request held its transaction (the server ended it after `idle_in_transaction_session_timeout`, 25P03, or the database restarted) answer 503 `busy` (`DatabaseConnectionError`), never 500 and never 2xx. TypeORM leaves such a runner released with its transaction still marked active: `TenantInterceptor` refuses to report a commit on it, and the filter turns the "already released" errors of later queries into the same 503. Nothing the request wrote is committed. The liveness route (`/health`) is never looked up and opens no transaction: it answers as long as the process serves requests.
- **Frontend autosave** (`frontend/src/hooks/useAutosave.ts`): `retry` and `busy` are retried by itself after the longer of the server's `Retry-After` and its own backoff (1, 2, then 4 s), at most three times per pending edit in all (flushes included), with the edit kept on screen; once they are spent the edit stays pending and marked not saved, an explicit save or navigation tries once more, and leaving asks for confirmation instead of blocking. A conflict (`duplicate`, `parent_gone`, `in_use`) is not retried: the message shows and the screen reloads the server state. Workspace pages (OPEX, CAPEX, incident, contributor) buffer unsaved fields per item (`frontend/src/hooks/patchBuffer.ts`): a field is only ever sent to the item it was typed on, and a refused field is never sent again with a later edit. A 409 `edit_conflict` (someone else changed the field, see "Edit conflicts" below) is neither retried nor dropped: the autosave shows its `conflict` state, the page keeps the edit and asks the user per field (`EditConflictBanner`), and leaving with a choice not made asks for confirmation, through the workspace's own controls and through the app's links (`frontend/src/hooks/leaveGuard.ts`).
- **Client abort** (`backend/src/common/request-finalizer.middleware.ts`): a response closed before it finished, while the request still holds its runner, rolls the transaction back and releases the connection; the handler's later queries fail at once (`ClientAbortedError`) instead of running outside the transaction. The exception filter answers nothing: it drops the abort's own fallout (`ClientAbortedError`, TypeORM's "already released" errors, a refusal below 500) and logs any other error at error level. One warning line, `client aborted, transaction rolled back`; an abort that lands during the COMMIT leaves the commit to finish and says `client aborted during the commit, its changes may be saved`. A handler that answers itself (`@Res()`, the file downloads) ends its response while `TenantInterceptor` commits: the finalizer then leaves the runner to the interceptor and sends nothing on that connection.
- Outside a request (public endpoints, scheduled tasks, directory sync) `withTenant()` in `backend/src/common/tenant-runner.ts` opens an equivalent scoped transaction.
- The host-resolution path is `createRequestTenancyMiddleware` (`backend/src/common/tenancy/request-tenancy.middleware.ts`), mounted by `applyTenancyAndPipeline` (`backend/src/http-app.ts`, called from `backend/src/main.ts`). A failed tenant lookup (pool exhausted, database down) answers 503 `busy` instead of going on without a tenant; an unknown tenant answers 404 `TENANT_NOT_FOUND` as before. A tenant whose sample data status is `resetting` gets 409 `tenant_resetting` on its write requests (reads, token refresh and sign-out go on), so nothing written during the reset survives it.
- **Sample data** (cloud only, `backend/src/demo-data/demo-data.service.ts`): an administrator loads the Fromage & Co set into a workspace still in its starting state (no business data, no configuration a reset would erase: own charts of accounts or accounts, calendars beyond the starting company's, dimension values other than the seeded values of the recommended dimensions, in any of the four seed languages, or of the three CAPEX dimensions of older tenants, portfolio classification, AI integrations and agents). The API runs `fixtures/fromage-co/setup-tenant.mjs --server-mode` as a child process (no shell, an environment of `PATH`, `NODE_ENV` and the `KANAP_DEMO_*` inputs only, the administrator's access token in that environment only) against itself on `127.0.0.1:$PORT` with the tenant's Host. The state lives in `tenants.metadata.demo` (`idle`, `loading`, `loaded`, `failed`, `resetting`), written by conditional updates of that key with a run id, so several API processes agree on it. A failed, timed out (12 min, and 60 s under the access token lifetime) or interrupted load is reset to the post-activation state (`TenantResetService`) once its process has ended. A load or a reset whose heartbeat (15 s, one write at a time) is older than 2 minutes was left by a stopped API process: the lead process (at start-up, then every 2 minutes) and every status read take it over. Loads over every tenant are capped by `DEMO_LOAD_MAX_CONCURRENT` (default 2), claimed under one advisory lock.

### Budget Writes: Lock Order and Freshness Counters
- **One lock order** for every writer of an OPEX or CAPEX line's budget (`backend/src/spend/budget-locks.ts`, plan planning/perf-scale lot 3B): (0) a bulk operation first takes the tenant's budget-operations advisory lock; (1) the line, `FOR NO KEY UPDATE` (`FOR UPDATE` before its delete), several lines in id order (`lockBudgetYear` for every line of a year); (2) its versions, several in id order; (3) the months of a version, created then locked in period order (`amounts-write.util.ts`, which locks the version again first); (4) the round-input records in column order, then their costed lines; (5) allocations, URL links, applications, projects and contacts. Writers of one line therefore take turns. Paths: item update (API, AI, both item CSV imports), version create and PATCH, amounts (`bulk-upsert`, column copy and clear, both CSV imports), costed lines, allocation saves and copy, line delete (bulk deletes in id order), contacts, relations and links of the line, the AI financial plan, relation and business record paths, which lock before they compare what the preview saw, and the FX pin or unpin of a freeze or unfreeze (every version of a year). One exception is left as it is: deleting a supplier, a company or a user sets the lines that name it to NULL (`ON DELETE SET NULL`) in the order PostgreSQL finds them, outside the id order and without the tenant lock; against a bulk operation that holds one of those lines and writes a reference to the deleted row, one side can end with a deadlock, answered 409 `retry`. Rare, and retried as is.
- **Targeted writes**: a line update (`item-locked-update.ts`), a version PATCH (`updateBudgetVersionUnderLock` in `budget-version-ensure.ts`) and a link PATCH read the row again under its lock and `UPDATE` only the columns the request supplied (plus `updated_at`, and the derived status and end of validity of a line when they change), never `save()` of a row read before: a column another request committed meanwhile stays, and `resolveItemWrite` (chart of accounts, cost center) checks the locked row. The audit `before` is the locked row; every audit row is stamped `clock_timestamp()` (the moment of the write, not the start of its transaction), so a record's history follows the order its changes were committed in.
- **Edit conflicts** (plan planning/perf-scale lot 3C, decisions D2 and D3; contract in `backend/src/common/edit-conflicts.ts`, OPEX and CAPEX line PATCH first through `spend/item-edit-conflicts.ts`): a PATCH body may carry `base`, per changed field the value the user's edit started from (analytics values per dimension: `base.analytics_values.<dimension id>`). Without `base` nothing is compared (the AI, the CSV imports, older clients). Under the line's row lock, after `resolveItemWrite` and before the UPDATE, each field the request changes and names in `base` is compared with the stored value (`sameFieldValue`: blank text and null are empty, texts trimmed, ids without case, timestamps as instants, numbers numerically; the AI preview's comparison uses the same function). A field differs when someone else changed it meanwhile; a field already holding the requested value is no conflict; two edits of different fields never conflict, nor two dimensions; the status follows the end of validity and is never compared. Any conflict refuses the whole request (nothing written, the other fields of the request included: one request is one action of the user, such as a company and the account it clears, and the client then knows that nothing of it is saved): 409 `{ code: 'edit_conflict', row_version, conflicts: [{ field, base, current, mine, labels: { base, current, mine }, changed_by: { id, name }, changed_at }] }`. `labels` name id values (supplier, company, account, owners, project, contract, cost center, analytics value). A currency compares without case (a field may bring its own equality, `EditedField.same`). Who and when come from the latest audit row of the line that changed the field and wrote the current value (`idx_audit_log_tenant_record_created`); a value no audit row explains was written outside the audit trail (a referenced row deleted by `ON DELETE SET NULL`, a script): nobody is named, never the line's last editor, and the time is the line's `updated_at`. The request is checked (`resolveItemWrite`, 400) before it is compared, so a refused field of a request answers 400 even when another field of it conflicts. On the client, `PatchBuffer` keeps each field's base from its first keystroke until it is saved (a field typed again while being sent starts from the value being sent; a refusal gives the older base back), every overview, drawer and metadata field of the OPEX and CAPEX workspaces goes through it, and a refused edit is parked whole until the user chooses: "Keep their value" drops the field and shows their value from the answer (the end of validity with its status; the company and the account together: keeping their company or their account drops the user's other one, and decides its row), "Apply yours" sends it again with their value as base. A parked edit is never sent with another one (the 400 would drop it): an edit of another field of the line goes alone, an edit of a parked field joins it and waits (the banner shows that newer value as the user's), and once every choice is made what is left goes in a request of its own. A pick waits for the text still in its typing pause and goes after it, in its own request. Disabling a line with no end of validity sends the status alone (the server sets the date, or keeps one already passed), so two windows disabling the same line are no conflict. The banner says "You changed this field in another window" when the change is the user's own, never shows an id (a record gone is said so), scrolls past 40% of the screen, is a labelled region with a polite live region for its title, and hands the focus to the field or the content column after the last choice. The OPEX and CAPEX buffers live for the session (`useSharedPatchBuffer`, one per kind of page, cleared by `AuthContext` when a session ends or starts; another tenant is another address): a line left with a choice waiting by the browser's back button, or a save answered with a 409 after the page went, shows its banner and the user's values again on the next visit, and the other lines of the workspace name it with a link to it. A tab change keeps the choice and the banner without asking; previous/next and close ask first; the app's links (left menu, top bar, user menu, any in-app `a[href]`) ask the page through its leave guard (`leaveGuard.ts`, a capture click listener installed by `Layout`, since `BrowserRouter` has no navigation blocker); a hard unload warns. The browser's back and forward buttons are not asked (no blocker): the session buffer keeps the choice instead.
- **Budget and allocation edit conflicts** (plan planning/perf-scale lots 3D and 3E, decisions D2, D3, D5; contract in `backend/src/spend/budget-edit-conflicts.ts` and `backend/src/spend/allocation-save.ts`). - **Budget statement triggers and stale statistics** (migration `1853850000000`, plan planning/perf-scale item 4C bis). Every scan of a budget table inside a trigger carries the tenant's row level security filter. When a table's statistics predate its rows, taken while its pages held no live row (after a purge, after a large first import that failed and rolled back, an ANALYZE of an empty table), the planner reads it as one row, or the tenant as a fraction of a percent of it, whatever it now holds. The 2A and 3B functions joined their keys (an `unnest` of arrays, or a transition table) to the versions, lines and totals tables, so the planner put those tables on the outer side of a nested loop: the tenant's whole table scanned once per key. On 25,000 versions, one statement inserting 1,000 round inputs took 53 s, every statement of 1,000 to 50,000 months or round inputs ran past the 30 s request timeout, and every single-version write scanned the tenant's versions (about 72 ms instead of 0.2 to 0.5 ms: the budget rows import of the perf tenant went from 1.3 s to 129 s per 1,000 rows). The functions were replaced with bodies that give the same counters, totals and locks in the same order, and follow five rules (any new statement trigger on the budget tables follows them too; `budget-trigger-stale-statistics.integration.spec.ts` checks them with statistics taken on empty tables and, inside its transaction, the primary keys of the versions and round inputs dropped, so that a read per key is quadratic wherever the spec runs):
  1. No join. A transition table is only filtered, grouped or unioned; the old and new rows of an UPDATE are paired by grouping them on their identity and the compared columns (`HAVING count(*) = 1` is a changed row, or one without its pair), never by joining `old_rows` to `new_rows`.
  2. No read per key. The versions, lines, round inputs and totals a statement touches are read by one statement over all its keys, `id = ANY (<array>)`, the key's tenant checked as text (`tenant_id::text || id::text = ANY (<pairs>)`), never as `tenant_id = <the key's tenant>`. With such statistics every index costs about the same for a lookup by id, and which one PostgreSQL picks depends on index heights, catalog order and the orderings a statement can use: the first bodies looked keys up one at a time, comparing tenant_id with the key's tenant, and a new database (CI on PostgreSQL 16, a new PostgreSQL 15) served each lookup through `idx_spend_versions_tenant_year`, reading the tenant's 25,000 versions for each of 16,000 keys, where `appdb_perf` used the primary key. Whatever the plan, one statement reads each table at most once: an index probe per key, or one pass over the tenant's rows with the arrays hashed. A read of one or a few keys may also take that pass, as any read by id of the application does under such statistics: one pass per statement, never one per key.
  3. A totals row is changed with `INSERT ... ON CONFLICT (version_id) DO UPDATE`, which finds it through the primary key without a plan, for the rows known to exist (step 3) as for the versions that gained months (step 4).
  4. Keys are de-duplicated before any read, and several rows are locked in id order by that one statement (`ORDER BY id` under `FOR NO KEY UPDATE`: the rows are locked as the sort returns them, whatever the scan) before they are updated, as 3B did; a single row is updated directly.
  5. Each function is set `plan_cache_mode = force_custom_plan`: a statement that reads a function variable is planned again on every call, with the arrays as constants (their length known, `= ANY` hashed), so a plan made while a table was small never serves it once large, inside one import transaction included. Statements over the transition tables alone keep the plan of their first call: they join nothing, so any plan is linear. Step 4 of the amounts function (the totals rows of versions that gained months) runs in the server's `auto` mode, set with `set_config(..., true)`, which the function's SET clause confines to the call: it reads no table, and it is the one statement whose foreign key checks run (one per created row), which the function's mode would plan again row by row. Cost: about 0.3 ms per single-version amounts statement over the 2A/3B bodies on fresh statistics (1.1 ms instead of 0.8 ms for an update of a version's twelve months); no measurable difference on the perf tenant's budget rows import (144.8 s and 140.3 s against 150.8 s and 141.7 s for the 2A/3B bodies, run back to back). `EXECUTE ... USING` gives the same plans but parses, analyses and applies row level security on every call: 17 % slower on that import, so not used.

- **Statistics after a large import** (plan item 4C bis, `backend/src/spend/budget-import-statistics.ts`): the budget rows import and the OPEX and CAPEX line imports, once at least 1,000 rows of their file were written (inserted or updated; not a dry run, not a refused file), commit the request and give its connection back before answering (`createRequestCommitThenRun`), then run `ANALYZE` on the tables they write (versions, months, round inputs, totals of each type written, plus the lines and their analytics values for a line import) on a pooled connection of their own, in the background (`trackBackgroundWork`: a stop waits for it), one short transaction per table so each table's lock is held only while it is sampled. A table the KANAP role does not own (owner or member of the owner role, the check of migration `1853820000000`) is skipped and named in a warning with the statement its owner can run, never logged as analysed. Lock timeout 5 s, statement timeout 5 min; a failure is one warning (autovacuum analyses later). After the commit, not inside the request: there ANALYZE would hold its locks until the import commits, delay the answer, and its in-place row counts would survive a rollback. Why at all: until autovacuum gets to them (a minute or more after the commit, never for a change under 10% of a large shared table), lists and reports read the new tenant's tables with the old statistics (74 ms instead of 8 ms for a 300-line list in lot 2A). The CSV project will rewrite these importers; the call stays the last line of the three routes.

### Budget Line Nature
- **Workspace addresses**: both natures open at `/ops/budget/BL-n`, optionally followed by the tab. `/budget-lines/resolve/:ref` supplies the current nature before child APIs load. UUIDs and legacy OPX/CPX references are replaced in the address while preserving the tab and query. Former `/ops/opex/:id` and `/ops/capex/:id` addresses redirect there; a plain number keeps its legacy prefix. Creation uses `/ops/budget/new?nature=opex|capex` (OPEX by default). Notification links use the native BL number, and Plaid resolves the nature of budget links within the tenant.
- **One family, two natures** (plan planning/budget-unifie.md, lots Z0 and Z1): every budget line is a row of `spend_items` with its `nature`, `opex` or `capex` (migration `1853950000000`: `NOT NULL DEFAULT 'opex'`, CHECK `spend_items_nature_check`, index `(tenant_id, nature)`), and its children are rows of the `spend_*` tables (versions, months, totals, column rounds and costed lines, allocations, analytics values, contacts, links, attachments) and of `application_spend_items`, `asset_spend_items`, `contract_spend_items`, `portfolio_project_opex` and `portfolio_request_opex`. Migration `1853960000000` added `ppe_type`, `investment_type` and `priority` (nullable); since lot C1 no code reads or writes them (see "CAPEX criteria" below), lot C2 drops them. Migration `1853970000000` moved every CAPEX line and its children out of the `capex_*` tables, keeping each UUID, `row_version` and `budget_rev`. The `capex_*` tables stay, dormant, until lot Z2 drops them: nothing reads or writes them, and their search triggers and three `RESTRICT` keys are gone. Tasks keep `related_object_type = 'capex_item'`.
- **Numbers**: `item_number` is the line's `BL` number, from one sequence for both natures (`item_sequences`, key `spend`). `legacy_number` (unique per tenant when set) keeps the reference of before: `OPX-n` (n is the line's own number) or `CPX-n` (the old CAPEX number; the `capex` key still numbers the lines created through the CAPEX routes). In `common/resolve-item-id.ts`, `/spend-items/:id` takes a UUID, `OPX-n`, `BL-n` or a plain number of an OPEX line, and `/capex-items/:id` a UUID, `CPX-n`, a plain number (read as `CPX-n`) or `BL-n` of a CAPEX line. The id or reference of a line of the other nature is a 404.
- **The rule**: no code reads or writes a line, or a child of a line, without naming its nature (`backend/src/spend/budget-nature.ts`):
  - every statement on `spend_items` names it (`natureAnd(alias, nature)`, `naturesAnd(alias, natures)` for a statement that reads several natures (the budget file), `nature` in a TypeORM `where`, `linkedLineOf` for a child, `lineNumberSql` for the number a nature shows). Nature-specific entries of the scope tables point at `spend_*` with their nature. The unified list engine alone has a scope without a nature predicate: `SUMMARY_SCOPES.all`, explicitly marked `allNatures: true`. `assertScopeNatures` refuses at load an entry that reads `spend_items` without a nature or this marker;
  - the locks of `budget-locks.ts` name it, so they gate every writer: a line of the other nature is not locked, and its caller answers 404 or skips it;
  - a route addressed by a child's id finds the child's line through `findBudgetLineOf` / `budgetLineOfChild` or a lock first. A child of a line of the other nature answers 404;
  - one service per concern carries the nature as a field: `CapexItemsService` (and the CAPEX versions, amounts, allocations, contacts and delete services) is its OPEX twin with `nature = 'capex'`.
- **Unified reads** (lot U1): `/budget-lines/summary` and its totals, filter values, ids, neighbors and aggregate routes use the same SQL list engine with the `all` scope. Rows expose native `product_name`, `description`, `item_number`, `nature`, `reference` (`BL-n`) and `legacy_number`; the CAPEX alias presenter is not applied. The scope reads shared, OPEX and CAPEX dimensions and both task object types. `nature` is a filter, sort and aggregate key. Quick search accepts BL numbers and legacy references. The neutral resolver accepts a UUID, `BL-n` or bare BL number, `OPX-n` and `CPX-n`, scoped to the tenant and explicitly both natures. Mixed bulk deletion partitions and locks the selected lines in one query before calling each nature's delete service; unknown or foreign ids use the existing per-item failure path. The neutral budget-file export uses `all`, whose loader explicitly names both natures with `naturesAnd`; existing exports and imports retain their nature-specific behavior. Consolidation fields keep the existing accounts read gate. All routes use the `budget` right (reader for reads, admin for bulk delete and export).
- **Rights** (lot R): one permission resource, `budget`, covers every budget line, OPEX and CAPEX alike; no guard, AI policy, budget file check or screen tells the natures apart for rights. Migration `1853990000000` keeps each role's access: its `budget` level is the highest of its `opex` and `capex` levels as the guard of before read them; a row that guard gave no access with gives none (a `manager` row, ranked 0; a row of another tenant than its role), and a `budget` row written before lot R (read by nothing) is replaced, or deleted. It runs on the tenants that still hold `opex`/`capex` rows only, logs each role whose levels differed or that had such a row, updates the built-in Budget Administrator's description when it is still the one seeded before, and checks its result; its `down()` puts the merged level back on both. `opex` and `capex` stay aliases of `budget` in `permissions.service.ts` (`RESOURCE_ALIASES`): a leftover row (a tenant export or a database of before) is read as `budget` at the higher level, and a role saved with those keys is saved as `budget` (keys merged at the highest level, a `null` removes the right only when every key naming it is `null`, the rows of the old names replaced). The nature stays a property of the line, and the nature predicate alone keeps a line out of the routes of the other nature.
- **CAPEX routes**: `/capex-items*` and `/capex-versions*` (`spend/capex-*.controller.ts`) are aliases on those services. They keep the contract of before for one version, until the unified screens (lot U), with the `budget` right since lot R. `spend/budget-line-presentation.ts` gives a CAPEX line its old shape: `description` is `product_name`, `item_number` is its CPX number, and it has no `product_name`, `contract_id`, `nature` or `legacy_number`. Its children name it `capex_item_id`. A CAPEX `description` input is written to `product_name` (`item-write.util.ts`), except in a body that names the columns (`fields: 'columns'`, the budget file). Every line of both natures also returns `reference` (`BL-n`).
- **Audit labels**: the audit rows of a CAPEX line keep their labels of before (`capex_items`, `capex_versions`, `capex_amounts`, …; one table of correspondence, `auditTableOf` in `budget-nature.ts`) and the CAPEX shape, so the history and the conflict checks read the field names they knew.
- **Outside `spend/`**: the SQL that reads `spend_*` names the nature too: the chargeback report (its `scope`: OPEX by default, CAPEX, or both natures named explicitly), the "used by N lines" counts of each nature (accounts, charts of accounts, cost centers, working-day calendars, dimensions and values, tenant statistics, reference checks), the expiry reminders, the freeze's FX pin, the currency page's budget years, the stale tasks of the dashboard, the task labels and targets, the supplier contact propagation, the link lists and counts of applications, assets, contracts, projects and requests, and the AI reader and resolver (`budget-lines.registry.ts`, on `spend_items` with both natures named by its statements). A bulk replacement of an object's OPEX (or CAPEX) links lists, keeps and removes the links to lines of that nature only, and refuses (400) an id that names no such line of the tenant.
- **Not restricted, on purpose**: the statements about every line whatever its nature: the hourly lifecycle status sync (a status derived from `disabled_at`), the FX ingestion's currencies in use, the demo data's emptiness check, the tenant purge and the tenant reset.
- **Search**: the logical types of the index follow the nature. An OPEX line has one entry of type `spend_items` (`OPX`, its number) and a CAPEX line one of type `capex_items` (`CPX`, its legacy number, titled with `product_name`). One trigger on `spend_items` (`search_index_sync_spend_items`) routes by `NEW.nature` and deletes the entry of the other type. `search_index_refresh_spend_items` and `search_index_refresh_capex_items` each read their nature and purge an entry whose line is gone or of the other nature. `search_index_refresh_budget_lines` (analytics value changes) hands each nature's ids to its own refresh, and `search_index_refresh_tasks` labels a `capex_item` task from its CAPEX line. Since migration `1855960000000` both natures index the same weight-C text from `spend_items`: description, supplier, paying company, account name, account number, notes and the names of linked contracts. The migration reindexes each tenant's CAPEX lines.
- **CAPEX criteria** (lot C1): the PP&E type, investment type and priority of a CAPEX line are the values of three ordinary dimensions every tenant has, `ppe_type`, `investment_type` and `priority` (`applies_to = 'capex'`, required, English names; `backend/src/analytics/capex-dimensions.seed.ts`; migration `1853980000000` for the tenants of its time, with its own copy of the table and of the SQL, kept equal by `analytics/__tests__/capex-dimensions-seed.spec.ts`). The migration links each CAPEX line to the value of its column, per active tenant, with row level security lifted and the statement triggers of `spend_item_analytics_values` off (`row_version` unchanged, so exported tokens and open workspaces stay valid), checks that no line with a column set lacks its link, and rebuilds the CAPEX search entries; its `down()` computes the columns again from the values (by name) and keeps the dimensions, values and links. A dimension column of the lists sorts by the value's position in its dimension, then by name (`FieldSql.position`, `budget-list.config.ts`), in the list and in the aggregate's key order.
- **Budget file** (lot C1b, `backend/src/spend/budget-file/`): one file for both natures, a `nature` column first and `item_number` written `BL-n`. The route gives a row's nature when the file has no `nature` column (a file of before); every check of a row follows its own nature (the dimensions it may fill and the required ones, the account's "Used for", restricted values, the freeze of its nature, the duplicate hint), and a row that names a line with another nature is refused (the type changes from the line itself, see "Change of type" below). Either route needs `budget:admin`, which covers both natures (lot R): the preflight reads the lines and names of both natures (`naturesAnd`), and the load locks the target lines of both in id order, in one statement (`lockBudgetLinesOfBothNatures`). `BL-n` names the line's own number on both routes, and so does a bare number in a file with a `nature` column; in a file without it a bare number keeps its meaning of before (`CPX-n` on the CAPEX route, the OPEX line's number on the OPEX route). `OPX-n` and `CPX-n` name it by `legacy_number` (an `OPX-n` also an OPEX line's own number). The load writes each line through the item service of its nature with `fields: 'columns'` (`product_name`; `description` for an OPEX line only, a CAPEX line's being ignored with a warning until lot U), and its freeze checks, round inputs, version locks and audit labels follow the line's nature; a new CAPEX line also gets its CPX number. The export writes the lines of the route's nature, a column per enabled dimension (empty on a dimension of the other nature), as `budget.csv`.
- **Change of type** (lot M, `backend/src/spend/budget-line-type-change.service.ts`; routes in `doc/api-reference.md`): a line changes nature through `GET`/`POST /spend-items/:id/change-type…` (and `/capex-items/:id/…`), `budget:member`. From its first year (the smallest `budget_year` of its versions, or a line without a version) the change is made in place: under the line's lock one UPDATE writes `nature` (and, reaching CAPEX, a CPX number from the `capex` sequence when the line has none; it keeps it back in OPEX), the line's tasks change `related_object_type` (`spend_item` ↔ `capex_item`, no activity entry), and the search trigger moves its entry. Everything else follows by the line's id. From a later year N the line ends on 31 December N-1 and a new line of the other nature is created through the creation of its type (`create`, so its write gate applies: a required dimension, an account of the other type and a disabled cost center are refused as on any creation); the versions of N and after move to it (`UPDATE spend_versions SET spend_item_id`; their months, totals, rounds and allocations follow by `version_id`), and it gets the contacts and the links to applications, assets, contracts, projects and requests (copied), the description (written by a column update for a CAPEX line, whose API names its title so). Tasks, attachments and web links stay on the old line: an attachment is never copied, since its delete removes the stored file without counting other references. The new line names the old one in `spend_items.predecessor_id` (migration `1854000000000`: `FOREIGN KEY (tenant_id, predecessor_id) REFERENCES spend_items (tenant_id, id) ON DELETE SET NULL (predecessor_id)`, unique partial index `(tenant_id, predecessor_id)`, so one successor per line; a column, no new table, nothing to add to the isolation or purge inventories). The workspace reads both directions (`budget-line-lineage.ts`). A non-zero amount in a column frozen for either nature, in the years that change, refuses the change (409); the dialog sends the `row_version` it read (409 `edit_conflict` when it moved). One audit row per line under the label of its nature after the change, with `operation: 'change_type'`, the natures, the start year, the references and the reason; its `row_version` differs from the one before, so the workspace names who changed the line. Locks: the line FOR NO KEY UPDATE, then the versions that move, no tenant lock (as a line delete). Task creation and update read their line FOR SHARE (`tasks-unified.service.ts`), so a task created or moved during a change waits and is refused for a line of the other nature instead of keeping the type of before; the task writes that read the task first set only the columns they change (`tasks/task-column-write.ts`: the status from the activity box, an edit through the line's route, an update by id, the closing of a task turned into a request), so a task read before the change never writes its relation back. The task CSV import gives a task named by a budget line's id the type of the line's nature. The audit row of the new line counts and names what was copied, per family (`copied`), with no row per link.
- **A version changes line only through a change of type**: `lockVersionWithLine` reads a version's line without a lock, locks that line, then locks the version only if it is still on that line and the line has the scope's nature. A writer that read the old line before a change from a later year finds the version on another line under its lock and answers 404, never writing a version through a line it does not hold, whatever the natures of the two lines are by then (the new line may have changed type again in place). The other writers of a version read it again under its line's lock and check its line (`updateBudgetVersionUnderLock`, the column and allocation operations, the AI).
- **Risks accepted with the change of type**: a version can be created again on an ended line for a year after its end, by the grid, the AI or a file exported before the change (`budget-version-ensure.ts`), as on any ended line: the lists, reports and chargeback leave it out (`versionWithinValidity`); a file exported before the change that names the line `OPX-n` (or `CPX-k`) no longer finds it in the other nature's list (`budget-file/preflight.ts`, a row error), `BL-n` does; the expiry reminders of a line ended by a change from a later year are sent as for any line that ends; an old link `/ops/opex/<uuid>` of a line now CAPEX answers 404 until the `/ops/budget/<ref>` routes (lot U); a freeze committed between the check and the commit of a change is not seen (the window of a line delete); the FX rate sets pinned on versions are left as they are (only versions without amounts in frozen columns change nature, and the reads convert with `fx_rate_set_id` or the live rates). Deleting a line that another line continues sets the successor's `predecessor_id` to NULL: that bumps the successor's `row_version` with no audit row, so its workspace says it changed elsewhere without naming anyone, and a budget file in progress on it is refused as stale; the same delete locks the successor outside the id order, so a bulk write that holds the successor and waits for the deleted line ends in a deadlock, answered 409 `retry` (`budget-locks.ts`). Every update of a task of a budget line reads the line `FOR SHARE` (`resolveTargetContext`), also when its relation does not change: during a bulk operation that holds the line for more than the lock timeout (5 s), the task update answers 503 `busy`.
- **Revert**: `1853970000000.down()` moves the CAPEX lines back into `capex_*`. It refuses while a CAPEX line has an empty CAPEX field, a `contract_id` or no tenant: revert `1853980000000` first, whose `down()` fills the fields again from the dimension values (a value added since, or no value, leaves the field empty and blocks this revert; a tenant without a dimension of a criterion's code, such as a tenant deleted before lot C1, keeps that field as it is, its lines counted in the log). A link already there is never changed by a rerun of `1853980000000.up()`: a criterion the previous version changed on a line between a revert and the next deploy is not taken back into the dimension value, and the log names those lines (`kept link(s) name another value than the line's column`, the first 50, with the column and the value) so that they can be fixed by hand. It also names the links it makes on a value CAPEX lines cannot choose (a dimension of that code kept as it is, whose value of that name is disabled or for OPEX lines only). `1853960000000.down()` refuses while a CAPEX line is in `spend_items`. A revert restores metadata: a stored file deleted since is not brought back, and the rows `up()` left out in `capex_*` (an allocation to a missing company or department, a child of another tenant than its line, named in its log) are lost. A rerun of `up()` copies no line of a tenant already moved (a line deleted since stays deleted) and refuses, before any write, a moved line that lacks its children or a totals trigger that does not fire.

### Referential Integrity
Every column that names a row by its id (`*_id`, `*_ids`, any `uuid` column other than `id`) has a foreign key, or an entry with its reason in `backend/src/common/reference-keys.inventory.ts`. The spec `common/__tests__/reference-keys.inventory.integration.spec.ts` reads the migrated database and fails on a column with neither.
- The delete action follows what the row means: `CASCADE` for a row that means nothing without the one it names (link rows, attachments, history, memberships, a user's own settings), `SET NULL` for a nullable reference (who created or leads something, a department, a phase, a classification item), `RESTRICT` only where the delete service refuses a record still in use and says why (companies, suppliers, a connection's equipment).
- A migration adds a key with `ensureReferenceKey` (`common/migration-reference-keys.ts`). It succeeds on any data: rows that name a row missing in their tenant are deleted (`CASCADE` keys), cleared (nullable columns) or kept under a `NOT VALID` key (a `NOT NULL` reference with nothing to fall back on), counted per tenant in the log; a rerun validates a key once its rows are fixed. Precedents: `1854070000000`, `1854090000000`, `1854160000000`.
- No key is possible on lists and polymorphic references. Their delete services clean them: a user leaves `tasks.owner_ids` and `viewer_ids`, a budget line or a contract deletes its tasks (`related_object_type`/`related_object_id`), an application, interface or request deletes its managed documents (`integrated_document_bindings`), and a company named in a year's default allocation method (`allocation_rules.company_ids`) cannot be deleted. Managed documents whose source record is already gone are released by the daily `attachment-orphan-cleanup` task, never deleted: unbound, moved to the unfiled documents of their library, kept with their files, one audit entry each. Records kept as written (`audit_log`, the AI activity tables, `search_index` maintained by triggers), identifiers of other systems, `tenant_id` (RLS and the tenant purge) and the dormant `capex_*` tables have no key either.
- Every key that deletes or clears rows (`CASCADE`, `SET NULL`) has an index leading with its columns (migration `1854180000000`), unless its table stays tiny and is listed in `UNINDEXED_DELETING_KEY_TABLES` with the reason. Without it, deleting the parent row reads the whole child table, every tenant included; an index on `(tenant_id, column)` is read in full. The same spec checks it.
- Known limit: the keys are single-column, on `id` alone. The migration repairs rows naming another tenant's row, and the application never writes one, but the database would accept such a row and cascade or clear it with the other tenant's parent. Keys on `(tenant_id, column)` into `(tenant_id, id)`, as for cost centers and analytics values, would refuse it.

### Data-scoped access

Data-scoped access limits a person to some companies and cost centres in the budget block: budget
lines of both natures, contracts, and every path that reads them. The database enforces it with
restrictive RLS policies that target one role only, so nothing changes for anyone else.

- **The model.** `users.data_access_mode` holds `all` (the default) or `limited`. A limited person
  has nodes in `user_data_access_nodes`: a company, a cost centre (a group or a leaf) or everything,
  each with `read` or `edit`. Reading follows the union of the nodes: a company reads the lines it
  pays and the lines charged to its own cost centres; a group reads its sub-groups and their cost
  centres, whatever their company; a cost centre reads the lines charged to it; everything reads
  all. A contract is read through its company, its place in the tree or one of its budget lines.
  Participations always open their object: IT or business owner of a line, contract owner, task
  assignee or owner (edit), task follower (read). An Administrator sees everything, cannot be
  limited, and is matched by role name as in `auth/business-contributor-scope.ts`.
- **Placement.** An edit node permits placing an object whose company or cost centre it covers. A
  line's paying company must be an edit company, or the company of its cost centre when that centre
  is covered in edit; a contract's company must be an edit company, or the company of one of the
  nodes covered in edit when its place in the tree is covered in edit. The rule holds on creation
  and on any change of company or place; a participation never permits placing or deleting.
  `data_access_placable_line(company, cost_centre)` and
  `data_access_placable_contract(company, place)` are the only definitions, called by the policies,
  the placement triggers, the write checks and the budget file preflight.
- **The role.** `kanap_data_limited` is `NOLOGIN`. The application role may take it (`SET ROLE`)
  but never inherits it: otherwise its policies would apply to every request. PostgreSQL 16 and
  later: `GRANT ... WITH INHERIT FALSE, SET TRUE`. PostgreSQL 15: the application role becomes
  `NOINHERIT` and gets `USAGE, CREATE` on `public` directly in each database it owns.
- **The role script.** `infra/scripts/data-access-role.sql` (`mode=install` or `mode=uninstall`)
  is the only step that needs a superuser or a `CREATEROLE` role. It is idempotent and runs before
  or after the migrations. CI runs it once before the migrations. QA and prod: the operator runs it
  once per server after the deploy, then restarts the API. On-premise: optional; without it, nobody
  can be limited. Dev (PostgreSQL 15): run it with `-v include_template1=on` on every database the
  application role owns, then once more to apply `NOINHERIT` (loop in the script header); new dev
  volumes get it from `infra/db-init/`. The option also grants on `template1`, so the databases
  created later (lane copies, test databases) let the application role create in `public`. By
  default the script requires and grants only the databases the application role owns: on a
  PostgreSQL 15 server shared with other applications, a grant on `template1` would reach their
  future databases too.
- **The policy set.** `data_access_expected_policies()` returns `(policy_name, table_name, command,
  fingerprint)`, the fingerprint being the md5 of the command and of the two policy texts.
  `data_access_sync_policies()` grants the role its rights on the tables and sequences the
  application role owns and recreates a policy only when it is missing or different: it compares
  the `COMMENT ON POLICY`
  `kda:<fingerprint>:<md5 of the deparsed expressions>`. A healthy database therefore starts without
  policy DDL and its exclusive table locks. A migration that changes the set redefines both
  functions with the complete list and calls the sync. Without the role, the sync does nothing. When
  the application role inherits the limited role, the sync drops every policy on the role and
  creates none (a warning): without that, the policies would apply to every request, migrations
  included. Limited persons are then refused (`KDA01`); unscoped persons are served.
- **The policies.** Restrictive, named `<table>_data_access_<command>`, `TO kanap_data_limited`,
  next to the tenant policies. Each starts with the context guard
  `(SELECT 1 WHERE current_setting('app.da_mode', true) = 'limited') IS NOT NULL`: the role taken
  without `data_access_apply` refuses everything. The subquery matters: a bare equality without
  statistics is estimated at 0.5% of the rows of every scoped table and turns the plans into nested
  loops, where the subquery is estimated at 99.5%. `read_all` (and `edit_all` for writes) is tested
  first, so Everything costs little. A child table's policy is a correlated `EXISTS` on its line,
  contract or task; deeper paths are cut by `SECURITY DEFINER` functions
  (`data_access_task_visible`, `data_access_contract_visible`,
  `data_access_searchable_task_ids`, `data_access_visible_contract_ids`) that read without policies
  and apply the same predicates. `DELETE` is refused on lines and contracts (reserved operations);
  children are deleted with their parent. Contract attachments and document links read only when
  the contract is directly readable, never through one of its lines.
- **Triggers.** `spend_items_data_access_placement`, `contracts_data_access_placement` and
  `tasks_data_access_placement` (`BEFORE UPDATE OF` the company and place columns, or the task's
  object) refuse, in mode `limited`, a new company or place that is not placable: the policies see
  only the new row, so an owner could otherwise move their line or contract out of the access and
  keep it. `spend_items_data_access_contract_link` and
  `contract_spend_items_data_access_link` (`BEFORE INSERT OR UPDATE`) require a readable contract
  and a modifiable line when a contract is linked to a line or a line to a contract; they run before
  the foreign key check and answer the same for a hidden and a missing object, so the key is no
  existence oracle. Outside mode `limited`, they do nothing.
- **The context.** `data_access_apply(user)` (`SECURITY INVOKER`) reads the person and the nodes,
  unfolds the tree, and sets nine transaction-local settings with `set_config(..., true)`:
  `app.da_mode`, `app.da_user`, `app.da_read_all`, `app.da_edit_all`, `app.da_read_companies`,
  `app.da_edit_companies`, `app.da_read_nodes`, `app.da_edit_nodes`,
  `app.da_edit_node_companies`. It then sets `jit = off` and takes the role
  (`set_config('role', 'kanap_data_limited', true)`); a second call in the same transaction
  re-reads the person and replaces the access (the preview uses it). `data_access_ctx()` exposes the
  settings as JSON for the list engine's "editable" column; the policies read them directly.
  `applyDataAccess()` (`data-access/data-access.ts`) calls it from these call points only:
  `TenantInterceptor`, the reconnection in `createTenantQueryRunner`,
  `AiTenantExecutionService.runWithContext`, and the public routes of the inline attachments. A
  limited person cannot run without a transaction (`{ transaction: false }` is refused), and the
  access is never set at session level. No other code changes the role (`SET ROLE`, `RESET ROLE`,
  `set_config('role', ...)`); a spec checks it.
- **Fail closed.** For a limited person, `data_access_apply` refuses when the person is not in the
  tenant (`KDA02`, answered 401 `INVALID_TOKEN`), and when the role is missing, inherited, cannot
  be taken or an expected policy is missing (`KDA01`, answered 503 `DATA_ACCESS_UNAVAILABLE`).
  Persons in mode `all` and Administrators never take the role. The availability check is
  informative; `data_access_apply` decides per transaction.
- **Startup.** The lead process (`data-access/data-access-availability.ts`, called from `main.ts`)
  runs the sync when the role exists and a grant or an expected policy is missing or different, or
  the role is inherited, with a 5 s `lock_timeout`; a failure is logged and retried at the next
  start. It then checks the availability (role, membership, inheritance, `CREATE` on `public` on
  PostgreSQL 15, policies and their fingerprints, grants and `EXECUTE` on the disclosures) and logs
  one `[DATA-ACCESS]` line. Every process caches the result for a minute; `GET /auth/me` returns it
  in `dataAccess`, with the person's mode and nodes. The check is informative only.
- **Controlled disclosures.** Three `SECURITY DEFINER` functions and one utility look beyond the
  access and return only what the model allows. The functions are tenant-filtered, refuse the
  limited role without context and check that the starting object is visible:
  - `data_access_hidden_count(type, id)` counts the lines or contracts linked to a visible object
    that the person cannot read, and the closed documents of a contract opened through a line;
  - `data_access_reference(type, id)` returns the reference of a linked line, never a contract
    (contracts have none);
  - `data_access_can_read(person, type, id)` tells whether another person can read a line, a task
    or a contract; notifications and "Send the link" use it;
  - `withFullDataAccess(manager, read)` opens a savepoint, makes it read only, leaves the limited
    role (`RESET ROLE`), runs `read`, rolls back to the savepoint (which restores the role) and
    checks the role came back; only the chargeback report (`spend/chargeback-report.service.ts`)
    and the contract coverage (`contracts/contract-budget.ts`) call it, and a spec checks those two
    callers.
- **Reserved operations.** A limited person cannot run the operations reserved to unscoped persons
  (tenant settings, bulk line operations, deletes of a line or a contract, user and role
  administration, audit log, organisation data, updates and deletes of suppliers and shared
  contacts, imports that update existing records, agent screens). One guard, two entry points:
  `@ReservedToUnscopedDataAccess()` on a route (refused by the tenant interceptor after it applied
  the access) and `assertUnscopedDataAccess()` for the paths outside the interceptor (Plaid writes,
  `runWithContext`); both answer 403 `DATA_ACCESS_LIMITED`.
  `data-access-reserved.inventory.ts` classifies every route of the controllers that hold a reserved
  operation as reserved or allowed with a reason, `data-access-paths.inventory.ts` classifies every
  path outside the interceptor transaction, `data-access-tables.inventory.ts` lists every table,
  view and function the access rules reach (the specs compare the catalog both ways), and
  `data-access-writes.inventory.ts` lists the TypeORM saves that rely on the write checks. A new
  route, path, table or save fails a spec until it is classified.
- **Administration.** `GET /users/:id/data-access`, `PUT /users/:id/data-access`,
  `POST /users/:id/data-access/preview`, `GET /companies/:id/data-access`,
  `GET /cost-centers/:id/data-access`, `GET /data-access`, `GET /data-access/export` and
  `POST /data-access/import?dryRun=` are reserved to unscoped persons who administer users (403
  `DATA_ACCESS_LIMITED` otherwise); `GET /data-access/placement-options` and `GET /auth/me` are open
  to the person. The preview follows the real path: in a savepoint it writes the proposed mode and
  nodes into `users` and `user_data_access_nodes`, applies the target's access with
  `data_access_apply`, counts lines (both natures) and contracts under the policies, rolls back to
  the savepoint, applies the caller again (which also resets the mode kept in memory for the
  transaction), and checks that the limited role and the settings are gone; a mismatch fails the
  request. Nothing is written.
- **Coverage.** The policies cover `spend_items` and the tables that follow a line (versions,
  amounts, allocations, round inputs and their lines, totals, analytics values, contacts, links,
  attachments, legacy tasks); `contracts` and the tables that follow it (contacts, compliance items,
  attachments, links, legacy tasks); the tables linking another object to a line (applications,
  assets, technologies, projects, requests) and to a contract (applications, assets, technologies);
  the tasks of a line or a contract and their elements, the link from a knowledge document to a
  task; and `search_index` for the entries of lines, contracts and their tasks.
  `contract_spend_items` has no policy (the contract policy cites it; the service checks its
  writes). `data_access_expected_policies()` is the list, and
  `SELECT DISTINCT table_name FROM data_access_expected_policies() ORDER BY 1;` names the tables.
- **Uninstall.** A lot's `down()` removes its policies through the sync. The script's
  `mode=uninstall` runs `DROP OWNED BY kanap_data_limited` in each database, then `DROP ROLE`, then
  `ALTER ROLE <app> INHERIT` on PostgreSQL 15. The direct grant on `public` stays.
- **Restore.** A backup restored on a server without the role brings back neither the policies nor
  the role's grants, and `pg_dump --no-privileges` drops the grants too. Limited persons are then
  refused until the script runs and the API restarts, which recreates what is missing.

### Authentication & SSO
- Local email/password + JWT is the baseline for every user. Access tokens come from `AuthService.signToken`; a refresh token is kept in an `HttpOnly` cookie (`auth-cookie.util.ts`) and feeds `/auth/me`, guards and the SPA's Axios interceptor.
- `JwtAuthGuard` verifies with a key built once from `JWT_SECRET` (`auth/jwt-key.ts`, rebuilt only if the secret changes). Given the secret as a string, jsonwebtoken first tried it as a public key (a thrown error) then built the key on every authenticated request: about 980 µs of main-thread time per request, 19 µs with the key built once (measured on Node 20).
- Microsoft Entra is the only SSO provider (no SAML, Google or generic OIDC). Each tenant connects one Entra directory via **Admin → Authentication**; the tenant row stores `sso_provider` (`none|entra`), `sso_enabled`, `entra_tenant_id` and `entra_metadata`, enforcing a strict 1:1 mapping.
- `EntraAuthService` downloads the discovery document and JWKS, builds authorization URLs, exchanges codes and validates `id_token` claims (audience, `nonce`, `tid`, `oid`). The issuer is validated against `https://login.microsoftonline.com/<tid>/v2.0` to support multi-tenant authorities. Env: `ENTRA_CLIENT_ID`, `ENTRA_CLIENT_SECRET`, `ENTRA_AUTHORITY` (e.g. `https://login.microsoftonline.com/organizations`), `ENTRA_REDIRECT_URI` (public HTTPS URL of `/auth/entra/callback`). The whole feature is gated by `ENTRA_SSO`.
- Setup flow: `POST /auth/entra/setup/start` (tenant admin, JWT; a `GET` variant exists for browser redirects) returns `{ url }` with a signed short-lived `state` carrying the OIDC nonce. The URL uses `prompt=consent`. The shared callback validates the nonce, persists the Entra tenant id and redirects to the tenant host's `/admin/auth?setup=success`.
- Login flow: `/login` offers "Sign in with Microsoft" → `GET /auth/entra/login?redirectTo=...` on the tenant host → 302 to Microsoft with signed `state`. The callback validates the token (nonce, `tid` vs `tenant.entra_tenant_id`), links or provisions the user (external subject first, then email), signs a short-lived handoff and redirects to `/login/callback#handoff=...`. The SPA redeems it through `POST /auth/entra/session` on the tenant host, which sets the refresh cookie and returns the access token; `AuthContext.login()` clears the fragment and navigates.
- Directory sync: a daily scheduled task (`entra-directory-sync.service.ts`) pulls users and manager relationships from Microsoft Graph per tenant, running under `withTenant()`, and reports `consent_required` when the app registration lacks permissions. Group sync is not implemented.
  - Permissions: the sync uses application permissions (client credentials, scope `https://graph.microsoft.com/.default`). The app registration needs `User.Read.All`, which also covers reading the manager. Without it the tenant reports `consent_required` and keeps login-time enrichment only. After consent is granted, `invalidateAppToken` drops the cached token, because a token issued before the grant lacks the new permission.
  - Lookup: users are read in batches by object id with `GET /v1.0/users?$filter=id in (...)&$expand=manager($select=id)`. An id missing from the answer is a user removed from the directory, and a user with `accountEnabled = false` is deactivated. KANAP disables the matching account in both cases. If a directory refuses the manager expansion, the read is repeated once without it, so the reporting line never costs a tenant its profile refresh or its removed-account detection.
  - Managers: Graph omits the `manager` property when none is set, it does not return `null`. "Not set" and "not returned" are therefore the same case, and an absent manager never clears a stored value (a degraded expansion would otherwise wipe an org chart overnight). A manager is applied only to a person who has a contributor row and only when the manager is already a KANAP user, through `TeamMemberConfigService` (same rules as a manual edit: not self, no cycle). Such a reporting line carries `manager_source = 'entra'` and is read-only in the app. A run that changes nothing writes nothing.
  - Sign-in token: the delegated sign-in scope is `User.Read`, below what Graph requires to read a manager. The sign-in profile read therefore asks for the manager and falls back to a read without it. In practice the nightly application-permission sync is what imports reporting lines.
  - Identity link: users are linked by the `oid` claim, stored in `users.external_subject`, never by `sub`. The link does not depend on the app registration: recreating the registration keeps every user linked, and only the admin consent must be granted again.
- **HTTPS requirement**: Entra redirect URIs must be HTTPS. In development use the same tunnel for the SPA, `ENTRA_REDIRECT_URI` and `VITE_API_URL`; nonce validation is stateless and needs no cross-subdomain cookie.
